# Vintazk 360 — Project Guide for Claude

A Django 6 **KPI dashboard** for a BPO/outsourcing org (Nexzys Intelligence / VINTAZK).
This file loads every session — keep it accurate.

## Stack & how to run
- **Dev = Docker only** (Postgres in a container). Staging = **Render** web service + **Render Postgres** (`DATABASE_URL`), files in **Cloudflare R2**. No SQLite.
- Start: `docker compose up --build`. App at http://localhost:8000.
- All Django commands run in the container: `docker compose exec web python manage.py <cmd>`.
- **No rebuild for code/template/CSS changes** — bind mount + auto-reload + tailwind watcher pick them up. Rebuild only for dependency / Dockerfile / compose changes. If the reloader wedges on an app rename, `docker compose restart web`.

## Compose services
- `db` — Postgres. `web` — Django dev server (`config.settings.dev`). `tailwind` — Node container that installs deps, vendors JS/fonts, watches & rebuilds CSS.

## Layout / conventions
- Apps live under `apps/` (import path `apps.<name>`, but each keeps a short `label` so DB tables stay unprefixed).
- Settings split: `config/settings/{base,dev,staging,prod}.py` (dev is default; staging inherits prod).
- Frontend: **Tailwind** via real Node build (not CDN). Source `static/src/input.css` → `static/css/output.css` (gitignored). Heading font **Space Grotesk** (vendored `static/fonts/`, Tailwind `font-heading`).
- **NO Flowbite** — it was removed (JS didn't init reliably). Don't reintroduce. Interactivity in plain Tailwind: dropdown → `<select>`, avatar menu → native `<details>`, modal → CSS `:target` (`.modal-overlay:target{display:flex}`, open via `href="#id"`, close via `href="#"`).
- **Toasts:** `templates/partials/toasts.html`, included from `base.html` **outside `<main>`** (main is the scroll container; a viewport-pinned toast must not live inside it). Bottom-right, one card per Django message, with a **5s countdown line**. The countdown IS the dismiss timer: JS removes the toast on the bar's `animationend`, so `.toast:hover` pausing the animation pauses dismissal too — one clock, not a bar plus a `setTimeout` that can drift. Colours come from `.toast-<level>` in `static/src/input.css`, which set a `--toast-accent` / `--toast-tint` custom property pair, so the markup carries one modifier class instead of four parallel `{% if %}` chains. Keyed off **`message.level_tag`**, not `message.tags` (tags can carry extra_tags and stop matching). Those `.toast-*` rules are plain CSS, not Tailwind utilities, so the dynamic class name is purge-safe, and they sit after `@tailwind utilities` so `border-left-color` beats the border utility on the same element.
- **Icons: django-icons + Font Awesome 4** (`{% load icons %}{% icon 'home' %}` → `<i class="fa fa-home">`). FA 4.7 CSS+webfonts vendored to `static/fontawesome/`, loaded in base.html. Use `{% icon %}` for new icons (fa4 names). Existing inline Heroicon SVGs may be migrated over time.
- Brand palette (Tailwind tokens): `ink` #040404, `brand` #4F3D67, `accent` #B27FA0, `blush` #DFADB6, `surface` #202427. Plus **semantic status tokens** `status.good` #4F3D67 (= brand, on-track), `status.warn` #D9A441 (muted amber, at-risk), `status.bad` #C25B6E (muted rose, below). On-track deliberately reuses brand purple so status stays on-brand yet distinguishable.
- **Logo:** PNG wordmark at `static/img/vintazk-360-logo.png` (committed, not a build artifact). Always render it via `{% include "partials/logo.html" with class="h-8" %}` — never hardcode another `<img>`. The "VINTAZK" text is **white**, so the logo only works on **dark** surfaces (sidebar, login left panel). On light backgrounds use the text lockup instead. Used in: base.html sidebar (all pages), login (both panels), and as the favicon.
- **Fonts:** body = **Montserrat**, headings = **Space Grotesk** — both vendored to `static/fonts/` via `@fontsource`, copied by the tailwind container on startup. Tailwind: default `sans` = Montserrat, `font-heading` = Space Grotesk.
- **Charts: Chart.js** (v4, vendored `static/vendor/chart.umd.min.js`, copied by the tailwind container; no CDN). Loaded per-page in `{% block scripts %}`, fed data via `{{ ...|json_script:"id" }}`. Used for the Operations "Actual vs Target" horizontal bar chart (normalized % attainment, direction-aware, colored by status token).
- Base shell `templates/base.html`: dark sidebar with **per-team dropdowns** (see below), top bar (page_title + `dept_badge` block + search + help + avatar dropdown), footer. **No sidebar collapse toggle** (removed).

## Anti-Slop Design Guidelines
**Every visual element must earn its place.** No gratuitous decoration, animation, or "creative" flourishes for their own sake. The goal is a professional, focused KPI dashboard for business users — not a tech demo.

**Core principle:** Purpose > decoration. Clarity > complexity. Restraint > flashiness.

- **Forms over flash:** Login, inputs, modals, and data-entry UIs must be scannable, fast, and task-focused. No twinkling stars, rotating orbs, glowing blobs, or constellation diagrams. Use spacing and typography to guide the eye, not animations.
- **No "dashboard theater":** Real data, clear charts, and crisp tables beat sci-fi effects. Pulsing nodes, network diagrams, and rotating rings distract from the metrics.
- **Color and gradients: sparingly.** The brand palette (ink, brand, accent, blush, surface, status tokens) is ample. Don't add extra shades, gradients, or shadows unless they create visual hierarchy or affordance.
- **Animation restraint:** Use `transition` for state changes (hover, focus, active). Avoid continuous animations (float, pulse, spin, twinkle, drift) on interactive elements or in the background. If you use animation, keep it under 300ms and tied to user action.
- **No em dashes in user-facing copy.** Anything a person reads (helper notes, labels, banners, flash messages, form errors, empty states, the generated CSV header) uses a full stop, a comma, a colon, or a rewrite instead. Two sentences beat one sentence with an em dash in it. This is a copy rule only: code comments and docstrings are unaffected. Applied across the KPI Management screens; the older screens still carry some in pre-existing copy.
- **The "remove and test" rule:** If you can hide an element and the page still works exactly the same, remove it.
- **Status over style:** When adding a visual effect, ask: "Does this communicate information or improve usability?" If the answer is "it looks cool," it probably stays out.

## Gotchas (learned the hard way)
- Django `{# #}` comments are **single-line only** — multi-line ones render as visible text. (Bit us repeatedly — in the sidebar and the modal. Keep every `{# #}` on one line.)
- Tailwind only compiles classes it finds as **literal strings** while scanning templates. Classes built dynamically in JS (e.g. `'bg-status-' + key`) get purged — reference each full class literally somewhere (it scans inside `<script>` too), or they won't exist in `output.css`.
- Don't put `hidden` and `grid` on the same element (both set `display`) — they conflict. To toggle a grid's visibility from JS, start `hidden` and apply grid via `[&:not(.hidden)]:grid`.
- In arbitrary Tailwind values, `theme(colors.brand-dark)` is invalid (dash) — use `theme(colors.brand.dark)` or a literal hex.
- Renaming/adding apps can wedge the dev-server autoreloader → `docker compose restart web`.
- Login-protected pages can't be screenshotted by headless-Chrome flags (can't POST login) — verify via markup/curl with a session cookie, or Django test client (`Client(SERVER_NAME='localhost')` + `force_login`).
- Adding a class only used in a JS string still needs a CSS rebuild to appear; the tailwind watcher usually catches it, but `docker compose exec tailwind npm run build:css` forces it.

## Sidebar navigation (BUILT)
- Each accessible team renders as a **collapsible dropdown** (native `<details>`) of its sub-pages; a team with only one page renders as a plain link. Sub-links are data-driven: the context processor includes a page only if its URL resolves (`<slug>:index` / `:import_data` / `:kpis` / `:kpi_management`), so new per-team pages appear automatically. Operations and Nexzys = Dashboard / Import Data / KPI Definitions / KPI Management; other teams = Dashboard only.
- **Teams can split into branches** (sub-teams) — the dropdown then nests one level deeper. Convention: the LOB app exposes `NAV_BRANCHES = [(slug, name), …]` from `apps/<slug>/branches.py`, and its URLs provide `branch_index` / `branch_import_data` / `branch_kpis` / `branch_kpi_management` taking the branch slug. The context processor discovers this by import — no registry in `core` to keep in sync. A branch team's own `:index` link stays labelled **Dashboard** — it *is* one (a rollup of every branch), and the nesting already shows it sits above each branch's own. (It read "Overview" until that page grew tiles and a chart.) **Sales is the only branch team** (seo / leadgen / transitions). VCT was briefly modelled this way too — it isn't; see the VCT/SMM/Content note below.

## Domain model — LINES OF BUSINESS (LOBs)
Each LOB = its own app under `apps/`, each a login-protected screen:
`sales, hr, academy, operations, finance, sitelead, vct, smm, content, nexzys` (+ `dashboard` overview, `core` shared).
Display names: Operations, Site Lead, Sales, HR, VINTAZK Academy, Finance, Visual and Content Team, Social Media Management, Content Writing, Nexzys.
**Always spell "Visual and Content Team" out in the UI** — "VCT" is for slugs, app names, and code only (migration `core.0004`).
There is **no `marketing` app** — it was split into `vct` / `smm` / `content` (migration `core.0003`).

### Two-dashboard model
- **Overall Dashboard** (`apps/dashboard`) — org-wide rollup, shared to EVERYONE, default landing on login.
- **Per-team/LOB Dashboard** — each LOB has its OWN dashboard = that team's KPI **scorecard** (Actual vs Target + status).

### KPI screens are SCORECARDS, not reference tables
Each KPI has a definition/formula/target/frequency, but the screen's job is to show/enter **actual** performance: **Actual vs Target + status** (on-track/below). Data enters TWO ways: **Excel import** OR **manual entry** (Add Record modal). Mockup ref: Import Data screen = stat cards + KPI Records table + Add Performance Record modal + Recent Import History.

### Operations specifics (current focus)
- Operations oversees MANY teams. **All 7 files in `Excel Files/` are Operations data** — different teams: BPAO, Adparlor, CS Reward (E-commerce), KPI Tracker teams (MediaOps, PubDev, WebDev, JAC, RDAT), ASC, PDDL.
- Two Excel data shapes: (1) **Monthly agent scorecard** (Agent × QA/Attendance/KPI/Behavioral → Performance Rating; metrics/weights vary per team) and (2) **OB call activity log** (ASC/PDDL: agent × date × call outcomes, appointments, revenue).
- The 6 "Operations KPIs" from the North Star image (Attrition, Client Retention, Billable Hours, CSAT, EBR, Seat Expansion) are the leadership ROLLUP.
- **Operations is the reference implementation.** Its pages (all data-driven from `_OPERATIONS_KPIS` in `apps/operations/views.py`, still static placeholder data): **Dashboard** (`:index`) = summary tiles + Actual-vs-Target bar chart + KPI cards grid; **Import Data** (`:import_data`) = stat cards, KPI Records table, Recent Import History, and an **Add Performance Record modal**; **KPI Definitions** (`:kpis`) = data-driven definition cards (name/category/description/Target/Frequency/"How it's calculated" formula).
- **Add Performance Record modal** (Import Data): pick a KPI → two inputs relabel to that KPI's formula parts (numerator/denominator) → live "How it's calculated" panel computes `num ÷ den × 100`, then direction-aware attainment vs target + status pill. All client-side JS, no persistence yet (Save is a mockup).
- **Attainment math** (shared by dashboard + modal): `up` KPIs = actual/target×100; `down` KPIs (e.g. Attrition threshold) = target/actual×100. Status: ≥100 on-track, 90–99 at-risk, <100 (else) below.
### Nexzys specifics
- **Nexzys = the internal technology / automation LOB.** Full four-page set built the same way as Operations (data-driven from `_NEXZYS_KPIS` in `apps/nexzys/views.py`, static placeholder values): **Dashboard** (`:index`), **Import Data** (`:import_data`), **KPI Definitions** (`:kpis`, also shows a "Data needed" chip list per KPI), **KPI Management** (`:kpi_management`).
- 8 KPIs: Automation Hours Saved, Automation ROI, System Uptime, IT SLA Compliance, New-Hire Provisioning, Workstation Readiness, AI Copilot Adoption, Security Incidents. Categories: Automation & AI / Infrastructure / Service Delivery / Security.
- **Not every Nexzys KPI is a percentage** — unlike Operations. Each modal KPI declares a `kind` that drives the Add-Record math and wording: `percent` (a÷b×100), `ratio` (a÷b, e.g. "3.4×"), `difference` (a−b hours saved), `days` (two date inputs, ready date − day 0), `count` (single input, major incidents). Security Incidents also carries an optional second pair for training-completion %.
- **Attainment edge cases handled in `apps/nexzys/views.py`:** zero-target KPIs (Security Incidents) are hit/miss, and attainment is bucketed on the *unrounded* value (`_shown()` keeps a 99.96%-vs-99.99% uptime miss from rounding up to "On Track"). Operations' copy of this math still rounds before bucketing.
- **Nexzys has no North Star metric yet** — the dashboard/definitions banner carries a descriptive line instead.

### Sales specifics
- **Sales is the first LOB that splits into branches:** `seo` (SEO & Google Ads), `leadgen` (Lead Generation), `transitions` (Transitions Team). All KPI data lives in `apps/sales/branches.py`; `apps/sales/views.py` holds the math and five views. URLs: `/sales/` (overview) + `/sales/<branch>/{,kpis/,import/,manage/}`.
- **Four templates serve all three branches** (`sales/dashboard|kpi_definitions|import_data|kpi_management.html`), driven by the `branch` context var — adding a fourth branch means one entry in `BRANCHES`, no new templates. `/sales/` renders `overview.html` — the team-level **Dashboard**, a rollup: summary tiles counting every branch's KPIs, a "Branch Attainment" chart (one bar per branch = mean attainment of its *scored* KPIs, so all 17 KPIs aren't repeated here), then one card per branch with its attainment, status split, and a link into its own dashboard.
- **Sales targets are RANGES, not single numbers** ("40–80/month"). `_attainment()` in `apps/sales/views.py` scores a band: inside the band = 100%; outside it, measured against the edge that was missed, direction-aware. CPL is the one `down` KPI (band ₱750–₱1,500 — a reduction journey, not a ceiling).
- **Some Sales KPIs have no target** (`target_min`/`target_max` = None): the derived rates, plus anything the business hasn't numbered yet. These get a fourth status, `monitored` ("No Target") — neutral slate, no progress bar, excluded from the chart and from the on-track/at-risk/below tallies. Any LOB with derived KPIs will need this.
- Modal `kind`s here: `count` (single tally — most Sales KPIs), `percent`, `cost` (a÷b shown as ₱).
- **Two data judgement calls, both flagged to the user:** "New Logos / Headcount" was split into two KPIs (Lead Gen 9–44 HC, Referral 4–18 HC) because the source row carried two bands; and CTR is `monitored` because the presentation's target is a click volume (500–1,000) while the formula is a percentage.

### Shared KPI page kit (use this for NEW LOBs)
- Operations, Nexzys and Sales each carry their own copy of the math + four templates (built one at a time, before the shape settled). **Everything since — HR, VINTAZK Academy, Finance, VCT, SMM, Content Writing — runs on a shared kit instead**, so a new LOB is a data module + a thin views.py, no new templates.
- `apps/core/kpi.py` — the math (`attainment`/`status`/`shown`/`scorecard`/`counts`) plus one context builder per screen (`dashboard_context`, `definitions_context`, `import_context`, `management_context`). Single targets and Sales-style **range** targets are unified: a single `target` is treated as a band of width zero, so one function serves both. `target=None` → `monitored` ("No Target").
- `templates/kpi/{dashboard,kpi_definitions,import_data,kpi_management,branch_overview}.html` — driven by a `scope` dict `{title, badge, blurb}` plus the context builder's output. `branch_overview` takes branches with pre-resolved URLs so it stays app-agnostic.
- `static/js/kpi-chart.js` + `static/js/kpi-record-modal.js` — the chart and Add-Record calculator, shared. **`./static/js/**/*.js` is in the Tailwind content globs** because the modal script builds status-pill class strings; without it they'd be purged. Vendored libs are deliberately NOT scanned.
- Modal `kind`s the shared script understands: `percent` (a÷b×100), `count` (single tally, second field hidden), `average` (a÷b + unit suffix — days, ratings), `ratio` ("3.4×"), `cost` (₱), `difference` (a−b), `days` (two date inputs), `net_percent` ((a−b)÷a×100 — accuracy net of errors), `variance` ((a−b)÷b×100, signed display but graded on |value|), `accuracy` ((1−|a−b|÷b)×100), `scaled` ((a÷b)×c — the only kind with a **third** input, added for DSO).
- `evaluate()` in the modal script may return a `score` separate from `value`, for KPIs where the number shown isn't the number graded (a −3.2% budget variance shows signed, grades as 3.2 against a ±5 tolerance). `apps/core/kpi.py` does the same server-side by storing the magnitude in `actual` and the signed string in `actual_display`.
- **Two-sided tolerances** ("within ±5%") are modelled as a `down` KPI over a `target_min=0 / target_max=5` band on the absolute value — so overspend and underspend are both penalised past the tolerance, and anything inside it is 100%. Verified: 0/3.2/5 → 100%, 6.5 → 76.9%, 12 → 41.7%.
- Migrating Operations/Nexzys/Sales onto this kit is still outstanding — they work, so they were left alone.

## Staging infra — Render + Cloudflare R2 (WIRED — connection only, no data yet)
- **Supabase is GONE** (removed 2026-08-05, replaced before any data existed). Don't reintroduce `apps/core/supabase.py`, the `supabase` package, `SUPABASE_*` settings, or the `supabase_status` command.
- **Two independent channels, don't conflate them:** (1) `DATABASE_URL` = Django ORM ↔ Postgres (dev: Docker container · staging: **Render Postgres**); (2) `R2_*` = uploaded files over the **S3 API** to **Cloudflare R2**. Dev keeps files on local disk.
- `apps/core/storage.py` — `get_client()` (`lru_cache`d), `is_configured()`, `bucket_name()`, `upload_fileobj()`, `signed_url()`, `object_exists()`, `delete_object()`, `reset_clients()`. Client is built **lazily** and imports `boto3` inside the function, so missing/unreachable creds can never block boot. `R2NotConfigured` (an `ImproperlyConfigured`) carries the fix in its message. Nothing reads or writes yet — wiring only.
- **Why boto3, not django-storages/`FileField`:** `db_schema.txt` models the pointer explicitly (`kpi_import_batch.storage_provider/_bucket/_path`), so a plain S3 client is the smaller fit.
- **R2 gotcha baked in:** botocore ≥1.36 sends a CRC32 checksum on every upload by default, which S3-compatible providers can reject — the client passes `request_checksum_calculation='when_required'` (guarded by `try/except TypeError` for older botocore). R2 has no regions: `region_name='auto'`, endpoint derived as `https://<account_id>.r2.cloudflarestorage.com`.
- Settings in `config/settings/base.py`: `R2_{ACCOUNT_ID,ACCESS_KEY_ID,SECRET_ACCESS_KEY,BUCKET,ENDPOINT_URL,REGION,TIMEOUT,SIGNED_URL_TTL,ENABLED}`. Four env vars are all that's needed; the rest have defaults.
- `config/settings/prod.py` — adds **WhiteNoise** (static files; no nginx in front of gunicorn on Render) and auto-trusts Render's `RENDER_EXTERNAL_HOSTNAME` in `ALLOWED_HOSTS` + `CSRF_TRUSTED_ORIGINS`, so a fresh deploy works before anyone types the generated URL anywhere.
- `config/settings/staging.py` — inherits prod hardening, HSTS off by default (sticky on a throwaway domain), and **refuses to start unless R2 is configured**.
- `manage.py storage_status [--ping]` (`apps/core/management/commands/`) — prints masked R2 config, which DB the ORM points at, whether the client builds, and optionally `head_bucket`s. **Not yet run against a live bucket** (no credentials issued yet).
- `render.yaml` (Blueprint: free Postgres + Docker web service, `DATABASE_URL` injected, `SECRET_KEY` generated, R2 secrets `sync: false`) + `render-start.sh` (migrate → collectstatic → gunicorn). Both run **at container start**, not in the Docker build — the build has no `DATABASE_URL`. No `healthCheckPath`: `SECURE_SSL_REDIRECT` would 301 a plain-HTTP probe.
- `boto3` in `requirements/base.txt`, `gunicorn` + `whitenoise` in `prod.txt` → **needs `docker compose up --build`**, not just a restart.
- **The bucket must stay private** — no r2.dev URL, no public custom domain. Downloads go through a Django view that re-checks team access and returns a short-lived signed URL.

## `apps/kpi` — the KPI data layer (TABLES BUILT, not yet wired to any screen)
- **One shared app, not one per department.** Every LOB app is a *screen* boundary (URL namespace + views), never a data boundary — all eleven had an empty `models.py`, now deleted. KPI rows are scoped by `kpi_definition.team_id` → `core_team`, which is the same key `team_required()` and the sidebar already use.
- Built from `db_schema.txt` — **read that file before touching these models**; it explains what each table is for. `kpi.0001_initial` (12 tables) + `core.0006_auditlog` (13th). Applied to Docker Postgres.
- **The core idea:** a KPI stores `expression` (a formula over named inputs) and `kpi_input` rows whose `key` is *simultaneously* the expression variable, the CSV column header, and the form field name. Adding a KPI adds zero lines of importer code.
- **`audit_log` lives in `apps/core`, not `apps/kpi`** — one deliberate deviation from the schema doc (noted there too). It records logins and user management as well, so the shared layer shouldn't depend on a feature app to write its own trail. Writer helper: `apps/core/audit.py` → `log_action(request, action=…, entity=…, entity_type=…, team=…)`, which swallows its own failures so logging can never break the action being logged.
- **`nulls_distinct=False`** on `kpi_definition`'s unique (team, branch, slug) — without it Postgres treats each NULL branch as unique and two *team-level* KPIs could share a slug. Needs PG 15+ (dev is 16, Render is 16).
- Targets are **always bands**: a single target is a band of width zero, `target_min`/`target_max` both NULL = `monitored` ("No Target"). Same rule the shared kit already uses in `apps/core/kpi.py`.
- `apps/core/kpi.py` (the attainment/status math) **has NOT moved** to `apps/kpi/scoring.py` yet — 7 LOBs import it and it works. Move it when the views switch to querysets (rollout step 5).
- Admin registers everything; the two history tables + import issues are read-only there, since they're append-only records.
- **`apps/kpi/formula.py` — BUILT.** The AST-whitelist parser/validator/renderer/evaluator (**never `eval()`**). Grammar: input keys, numeric constants, `+ - * /`, parens, and `abs/min/max/round/days_between`. Four entry points: `parse()`, `names()`, `validate(expression, keys)` (rejects unknown names, unreferenced inputs, formulas of pure numbers, and dry-runs against a sample row), `render_text(expression, labels)` → the `formula_text` sentence, `evaluate(expression, values)`. `days_between(a, b)` = `(b - a).days`. Gotcha handled: a called function is an `ast.Name` too, so `names()` excludes `Call.func` or `days_between` reads as a missing input.
- **`apps/kpi/csv_template.py` — BUILT.** Generates a KPI's CSV template (§D) from its own `kpi_input` rows in `position` order — `build(kpi)`, `columns(kpi)`, `filename(kpi)`, `period_label(frequency)`. **Generated on demand, never stored:** §A.6 requires a fresh download to carry the *current* `template_version`, so a file saved at creation time would go stale the moment a formula changed and the importer would reject the very template the screen handed out. Period formats: monthly `2026-07`, quarterly `2026-Q3`, weekly `2026-W32`, daily ISO, annually `2026`. One deliberate refinement of §D: `generated=` is a full ISO **timestamp**, not a bare date — `kpi_import_batch.template_generated_at` is timestamptz and two downloads on the same day must be distinguishable. The three comment lines are exactly three, as the file's own first line promises. The sample row is **blank** apart from the period, so nobody uploads a demo number as real data.
- **Not built yet:** the preset library data migration (`kpi.0002`), CSV **import**, and the remaining views' switch from static dicts to querysets.

### Operations Create-KPI form — the reference implementation (BUILT, writes to the DB)
- `apps/operations/forms.py` `CreateKpiForm` + `apps/operations/views.py:kpi_management` + `templates/operations/create_kpi_modal.html` + `static/js/formula_builder.js`. **This is the pattern to copy into the other LOBs** — don't re-derive it.
- **The inputs travel with the formula.** The JS builder serialises its operands into a hidden `inputs_json` field (`[{key, label}]`, canvas order); `clean_inputs_json()` checks them against `KEY_VALIDATOR` and `save()` writes the `KpiInput` rows. Without this a KPI has no CSV columns and no Add-Record fields — the single most important thing to get right when porting.
- One `save()` writes, atomically: the `KpiDefinition` (+ generated `formula_text`, unique slug), its `KpiInput` rows, and the seed `KpiFormulaHistory` row (`reason='Initial formula'`, `template_version=1`). The view then writes the `created`/`kpi_definition` audit entry — it holds the request, the form doesn't.
- **Slugs are made unique per team** (`-2`, `-3`) — `(team, branch, slug)` with `nulls_distinct=False` otherwise 500s the second time a KPI name is reused.
- **Targets: fill one side, get both.** A single figure is a band of width zero; both empty = `monitored`. Enforced in `clean()`.
- **Categories are team-scoped** — the `category` queryset is filtered to the team, plus a `new_category` free-text box that `get_or_create`s one, since `kpi_category` starts empty and an empty dropdown is unusable.
- **Gotcha — the modal is CSS `:target`, so a validation failure would re-render it CLOSED** with the errors invisible. The view sets `open_create_modal` and the overlay adds `!flex` (beats `hidden`'s `display:none`). Errors render via `templates/partials/field_errors.html`.
- JS `VARIABLE_PATTERN` must stay `^[a-z][a-z0-9_]*$` — the same shape as `KEY_VALIDATOR`. The builder also refuses to submit an input that the formula never uses.
- **Builder limitation:** the token canvas has no way to express a function call, so the preset list drops "Days between" and "Forecast accuracy" from `db_schema.txt` §A.4. `formula.py` accepts both — only the UI can't compose them yet.
- **KPI Management AND KPI Definitions are both DB-backed** (rollout step 5). One queryset (`_kpi_queryset`) and one row builder (`_kpi_row`) in `apps/operations/views.py` feed both, so the two screens can never disagree about a target or a formula. `_kpi_row` keeps the exact shape the static dicts produced, which is why neither template changed around the switch; `_management_rows` layers `csv_url` + the per-row `EditKpiForm` on top. The **CSV Template column** links to `operations:kpi_template` (`/operations/manage/<slug>/template.csv`), same `@login_required` + `@team_required('operations')` guard as every other page.
- **Operations' remaining two screens (dashboard, import) are still static** `_OPERATIONS_KPIS` / `_MODAL_KPIS`. Those dicts are also what `seed_operations_kpis` reads, so don't delete them yet.
- `manage.py seed_operations_kpis` (`apps/operations/management/commands/`) turns the six hard-coded Operations KPIs into real rows with inputs + a formula-history row. **Idempotent** — skips any slug that already exists. A command, not a data migration, because it inserts business data. Already run against Docker Postgres.
- **The Edit modal is live and carries the full formula builder** (`EditKpiForm`). Everything is editable except the `slug` — a downloaded CSV binds to it, so renaming the KPI is fine but its address is stable.
- **Three shared partials, use them for every LOB:** `partials/formula_builder.html` (takes `form` + a `uid` unique per instance on the page — it namespaces the `_formula_mode_<uid>` radios and the preset `<select>` id), `partials/category_picker.html`, `partials/field_errors.html`. `static/js/formula_builder.js` initialises **every** `[data-formula-builder]` on the page, so the `<script>` tag belongs in the page's `{% block scripts %}` **once** — not in a partial, or it executes per copy and double-binds listeners.
- **`BaseKpiForm` holds everything create and edit agree on**; `expression` + `inputs_json` are shared fields, so the builder works in both. The two subclasses differ only in consequence.
- **What a formula edit costs (§A.6), all in `EditKpiForm`:** changing `expression` **or the input key set** (add/remove/rename/reorder) bumps `template_version`, appends a `KpiFormulaHistory` row, and audits `formula_changed`. Rewording an operand's **label** is cosmetic — it regenerates `formula_text` but bumps nothing. Three separate properties keep these apart: `formula_changed` (keys+expression), `inputs_changed` (any input edit, labels included — so a relabel isn't misreported as "Nothing changed"), `targets_changed`.
- **`clean()` blocks removing an input that already has `KpiRecordInput` rows** — `KpiInput` is `on_delete=PROTECT`, so without the check `save()` would die on a `ProtectedError` mid-transaction. `_sync_inputs()` then does add/update/remove rather than delete-and-recreate.
- **Formula/target history rows record the formula or target in force FROM `effective_from`** — the *new* value, matching §12's and §11's column docs and §E.3's seed row. §A.6's prose ("preserve the previous") is satisfied because the previous one is the earlier row; storing the old value in the new row would duplicate the seed row.
- **Moving a target appends a `KpiTargetHistory` row** and audits `target_changed`; a formula change audits `formula_changed`; an edit doing both writes **both** rows. Anything else audits `updated`; changing nothing writes nothing. `change_reason` feeds both history tables' `reason`.
- **Category picker: one control, not two.** `CategorySelect` appends a `__new__` sentinel option ("+ Create new category…"); `CategoryChoiceField.to_python` maps it to `None` so it isn't a validation error, and `clean()` insists `new_category` is then filled. The text box is revealed by **CSS only** — `.category-picker:has(select option[value="__new__"]:checked)` in `static/src/input.css`, same no-JS spirit as the `:target` modals. On a failed POST the raw `__new__` stays selected, so the box stays open.
- **Delete is a SOFT delete** — `is_active=False`, audited as `deleted`, behind a `#kpiDelete-<slug>` confirm modal whose copy says nothing is destroyed. The KPI leaves the table and its `template.csv` starts 404ing (both querysets filter `is_active=True`), while records, history and audit rows survive. Design principle 7.
- **Gotcha — decimal comparison.** The DB returns `Decimal('3.5000')` where the form cleans `Decimal('3.5')`. `EditKpiForm._display()` normalises with `format(value.normalize(), 'f')`; without it every description edit would look like a target change and write a spurious history row.
- **One view, three modals.** Each form posts `_action` (`edit` / `delete`, absent means create) + `_slug` + `_page` to `kpi_management`, so the create form isn't bound to an edit's POST data. `open_create_modal` / `open_edit_slug` force the right modal back open on failure via `!flex`. Modal ids are `#kpiEdit-<slug>` / `#kpiDelete-<slug>`, not loop counters.
- **Gotcha, and it bites any `:target` modal that posts:** a browser **reattaches the request's fragment to a redirect whose `Location` has none of its own** (RFC 7231 §7.1.2). A successful save from `#kpiEdit-csat` therefore redirected to a fragment-less URL, the browser put `#kpiEdit-csat` back, and the modal sprang open again on the fresh page, looking like the save had failed. Fix: every success redirect goes through `_back_to_page()`, which appends the real anchor `#kpi-definitions` (the id on the table `<section>`). Give the Location its own fragment or the old one wins.
- **Pagination is live** — `PAGE_SIZE = 10`, `Paginator` + `page_obj` into the existing `partials/pagination.html` (which already supported a live page object). Only the current page builds `EditKpiForm`s. `kpi_count` on the stat card is the whole set, not the page. The table body scrolls (`max-h-[34rem] overflow-auto`) with a `sticky top-0` header.
- **Gotcha — Excel and UTF-8.** A plain UTF-8 CSV opened by double-click on Windows decodes as the ANSI code page, turning `÷ × · —` into `Ã· Ã— Â· â€"`. `csv_template.build_bytes()` prepends a BOM (`utf-8-sig`) — the one signal Excel honours — and the view serves that with `charset=utf-8`. Use `build_bytes()`, not `build()`, from any view.
