# Vintazk 360 — Project Guide for Claude

A Django 6 **KPI dashboard** for a BPO/outsourcing org (Nexzys Intelligence / VINTAZK).
This file loads every session — keep it accurate.

## Stack & how to run
- **Dev = Docker only** (Postgres + Valkey in containers). Staging = **Render** web service + **Render Postgres** (`DATABASE_URL`) + **Render Key Value** (`REDIS_URL`), files in **Cloudflare R2**. No SQLite.
- Start: `docker compose up --build`. App at http://localhost:8000.
- All Django commands run in the container: `docker compose exec web python manage.py <cmd>`.
- **No rebuild for code/template/CSS changes** — bind mount + auto-reload + tailwind watcher pick them up. Rebuild only for dependency / Dockerfile / compose changes. If the reloader wedges on an app rename, `docker compose restart web`.
- **`TIME_ZONE = 'Asia/Manila'`, not UTC.** Every timestamp on screen (the activity log, an import's "uploaded at", a record's "last updated") is read by somebody in the Manila office, and at UTC they all read eight hours early, which looks like a bug rather than a timezone. `USE_TZ` stays True, so Postgres still stores UTC and only the rendering moves. Anything comparing "today" uses `timezone.localdate()` and now means the local day.

## Compose services
- `db` — Postgres. `web` — Django dev server (`config.settings.dev`). `tailwind` — Node container that installs deps, vendors JS/fonts, watches & rebuilds CSS.
- `cache` — **Valkey** (Redis-compatible), the local stand-in for Render Key Value. `db` is the source of truth for application data and holds no cache; nothing in `cache` is durable and nothing needs to be (see the Caching section). Started with `--maxmemory 64mb --maxmemory-policy allkeys-lru`, persistence off.

## Layout / conventions
- Apps live under `apps/` (import path `apps.<name>`, but each keeps a short `label` so DB tables stay unprefixed).
- Settings split: `config/settings/{base,dev,staging,prod}.py` (dev is default; staging inherits prod).
- Frontend: **Tailwind** via real Node build (not CDN). Source `static/src/input.css` → `static/css/output.css` (gitignored). Heading font **Space Grotesk** (vendored `static/fonts/`, Tailwind `font-heading`).
- **NO Flowbite** — it was removed (JS didn't init reliably). Don't reintroduce. Interactivity in plain Tailwind: dropdown → `<select>`, avatar menu → native `<details>`, modal → CSS `:target` (`.modal-overlay:target{display:flex}`, open via `href="#id"`, close via `href="#"`).
- **Toasts:** `templates/partials/toasts.html`, included from `base.html` **outside `<main>`** (main is the scroll container; a viewport-pinned toast must not live inside it) **and outside `{% block layout %}`** (the login page replaces that block wholesale, and the session-expiry notice has to render there). Bottom-right, one card per Django message, with a **5s countdown line**. The countdown IS the dismiss timer: JS removes the toast on the bar's `animationend`, so `.toast:hover` pausing the animation pauses dismissal too — one clock, not a bar plus a `setTimeout` that can drift. Colours come from `.toast-<level>` in `static/src/input.css`, which set a `--toast-accent` / `--toast-tint` custom property pair, so the markup carries one modifier class instead of four parallel `{% if %}` chains. Keyed off **`message.level_tag`**, not `message.tags` (tags can carry extra_tags and stop matching). Those `.toast-*` rules are plain CSS, not Tailwind utilities, so the dynamic class name is purge-safe, and they sit after `@tailwind utilities` so `border-left-color` beats the border utility on the same element.
- **Right-click guard:** `templates/partials/context_menu_guard.html`, included from `base.html` **outside `{% block layout %}`** so the login screen (which replaces that block wholesale) is covered too. It suppresses `contextmenu` and opens a branded warning modal instead. **Text fields are exempt on purpose** (`input/textarea/select/[contenteditable]`, unless disabled or read-only): copy-paste into an Employee ID or a KPI figure is real work. It cannot use the `:target` trick, since only JS can cancel a context menu, so visibility is `.context-guard` / `.context-guard.is-open` in `input.css` rather than `hidden` + an arbitrary variant. **It auto-closes after 5s and the countdown bar IS the timer** (same one-clock rule as the toasts: it closes on the bar's `animationend`), but unlike a toast it does NOT pause on hover or focus, because the modal takes focus on open and sits under the pointer, so either pause would hold it open forever. Re-triggering restarts the bar, which needs a reflow read (`void timer.offsetWidth`) between removing and re-adding `is-running`. Note this is a deterrent, not a security control: the data is still in the DOM.
- **Icons: django-icons + Font Awesome 4** (`{% load icons %}{% icon 'home' %}` → `<i class="fa fa-home">`). FA 4.7 CSS+webfonts vendored to `static/fontawesome/`, loaded in base.html. Use `{% icon %}` for new icons (fa4 names). Existing inline Heroicon SVGs may be migrated over time.
- Brand palette (Tailwind tokens): `ink` #040404, `brand` #4F3D67, `accent` #B27FA0, `blush` #DFADB6, `surface` #202427. Plus **semantic status tokens** `status.good` #4F3D67 (= brand, on-track), `status.warn` #D9A441 (muted amber, at-risk), `status.bad` #C25B6E (muted rose, below). On-track deliberately reuses brand purple so status stays on-brand yet distinguishable.
- **Logo:** PNG wordmark at `static/img/vintazk-360-logo.png` (committed, not a build artifact). Always render it via `{% include "partials/logo.html" with class="h-8" %}` — never hardcode another `<img>`. The "VINTAZK" text is **white**, so the logo only works on **dark** surfaces (sidebar, login left panel). On light backgrounds use the text lockup instead. Used in: base.html sidebar (all pages), login (both panels), and as the favicon.
- **Fonts:** body = **Montserrat**, headings = **Space Grotesk** — both vendored to `static/fonts/` via `@fontsource`, copied by the tailwind container on startup. Tailwind: default `sans` = Montserrat, `font-heading` = Space Grotesk.
- **Charts: Chart.js** (v4, vendored `static/vendor/chart.umd.min.js`, copied by the tailwind container; no CDN). Loaded per-page in `{% block scripts %}`, fed data via `{{ ...|json_script:"id" }}`. Used for the Operations "Actual vs Target" horizontal bar chart (normalized % attainment, direction-aware, colored by status token).
- Base shell `templates/base.html`: dark sidebar with **per-team dropdowns** (see below), top bar (page_title + `dept_badge` block + search + help + avatar dropdown), footer. **No sidebar collapse toggle** (removed).

## Anti-Slop Design Guidelines
**Every visual element must earn its place.** No gratuitous decoration, animation, or "creative" flourishes for their own sake. The goal is a professional, focused KPI dashboard for business users — not a tech demo.

**Core principle:** Purpose > decoration. Clarity > complexity. Restraint > flashiness.

- **Forms over flash:** Login, inputs, modals, and data-entry UIs must be scannable, fast, and task-focused. No twinkling stars, rotating orbs, glowing blobs, or constellation diagrams. Use spacing and typography to guide the eye, not animations.
- **No "dashboard theater":** Real data, clear charts, and crisp tables beat sci-fi effects. Pulsing nodes, network diagrams, and rotating rings distract from the metrics.
- **Color and gradients: sparingly.** The brand palette (ink, brand, accent, blush, surface, status tokens) is ample. Don't add extra shades, gradients, or shadows unless they create visual hierarchy or affordance.
- **Animation restraint:** Use `transition` for state changes (hover, focus, active). Avoid continuous animations (float, pulse, spin, twinkle, drift) on interactive elements or in the background. If you use animation, keep it under 300ms and tied to user action.
- **No em dashes in user-facing copy.** Anything a person reads (helper notes, labels, banners, flash messages, form errors, empty states, the generated CSV header) uses a full stop, a comma, a colon, or a rewrite instead. Two sentences beat one sentence with an em dash in it. This is a copy rule only: code comments and docstrings are unaffected. Applied across the KPI Management screens; the older screens still carry some in pre-existing copy.
- **The "remove and test" rule:** If you can hide an element and the page still works exactly the same, remove it.
- **Status over style:** When adding a visual effect, ask: "Does this communicate information or improve usability?" If the answer is "it looks cool," it probably stays out.

## Gotchas (learned the hard way)
- Django `{# #}` comments are **single-line only** — multi-line ones render as visible text. (Bit us repeatedly — in the sidebar and the modal. Keep every `{# #}` on one line.)
- Tailwind only compiles classes it finds as **literal strings** while scanning templates. Classes built dynamically in JS (e.g. `'bg-status-' + key`) get purged — reference each full class literally somewhere (it scans inside `<script>` too), or they won't exist in `output.css`.
- Don't put `hidden` and `grid` on the same element (both set `display`) — they conflict. To toggle a grid's visibility from JS, start `hidden` and apply grid via `[&:not(.hidden)]:grid`.
- In arbitrary Tailwind values, `theme(colors.brand-dark)` is invalid (dash) — use `theme(colors.brand.dark)` or a literal hex.
- Renaming/adding apps can wedge the dev-server autoreloader → `docker compose restart web`.
- **`async-content.js` inserts a fragment's scripts ONE AT A TIME, waiting for each `src` to load.** It rebuilds every `<script>` to make it execute (innerHTML never runs them), and inserted together the inline block runs the instant it is added while the 200KB Chart.js is still downloading, so it finds no `Chart`, returns, and leaves a blank panel. **`async = false` does NOT fix this** — it orders src scripts against each other, but an inline script has nothing to wait for and runs immediately whatever the flag says. Only sequencing restores document order. This is why "Actual vs Target" was blank on every LOB dashboard: the two-stage render arrived after the chart was written and quietly broke it. Reproduced and fixed against the real fragment in headless Chrome (0 painted pixels before, a full chart after). Any src + inline pair in a `{% block scripts %}` depends on this.
- Login-protected pages can't be screenshotted by headless-Chrome flags (can't POST login) — verify via markup/curl with a session cookie, or Django test client (`Client(SERVER_NAME='localhost')` + `force_login`).
- Adding a class only used in a JS string still needs a CSS rebuild to appear; the tailwind watcher usually catches it, but `docker compose exec tailwind npm run build:css` forces it.

## Auth & access control (BUILT)
- Login-only (no self-registration). Split-screen animated login at `/login/` (North Star theme, sliding overlay). Login field is labelled **Employee ID** (username = employee ID for now, e.g. `2026-01-439`; real API wiring is a later step — a dedicated `employee_id` field + auth backend).
- Test superuser: `admin` / `testpass123` — **test credential, change before real use.** Demo users `demo_<team>` / `demo_manager` / `demo_admin` and `2026-01-439`, all password `demo1234` (throwaway).
- **Role-based access** (`apps/core`): `Team` model (one row per LOB, `slug` = URL namespace) + `UserProfile` (OneToOne, `role` ∈ superadmin/admin/manager/**user**/**viewer**, M2M `teams`). Everyone sees the shared Dashboard.
- **SEVEN roles, and access has TWO axes that cross** (`apps/core/access.py`, Part C of `db_schema.txt`). *Team reach*: superadmin, **admin**, **finance**, **hr** and **viewer** (or a Django superuser) → every team; manager and user → their `teams` M2M. *Write permission*: superadmin / admin / finance / hr / manager → yes; **user and viewer are read-only**. A viewer reaches everything and may change nothing, which is exactly why one ladder cannot model this. The restricted departments then come off the reach of everyone who does not hold them (see RESTRICTED DEPARTMENTS below).
- **FINANCE and HR are roles, not departments-you-are-assigned-to** (`UserProfile.Role.FINANCE` / `.HR`, migration `core.0012`). They are the only way into the two restricted departments short of being a Super Admin, and **each opens its own and not the other**: the Finance role reaches Finance, the HR role reaches Human Resources. Otherwise they sit in `WRITE_ROLES` and `ALL_TEAM_ROLES` and **not in `ADMIN_ROLES`**, which is the whole difference from an Admin: they write every team's figures, and **User Profiles, the activity log, deactivating an account and deleting a KPI are all closed to them** (all four ask `is_admin` or `is_superadmin`). Nothing needed a fourth membership set, so a screen cannot forget them.
- **Only a Super Admin hands out Super Admin, Finance or HR** (`access._SUPERADMIN_ONLY_ROLES`). The last two are there for the same reason as the first: each opens a department an Admin cannot reach, so granting one would be handing out access the granter does not have. **`can_manage_role()` asks the same set from the other end**, so an Admin can neither create nor demote a Finance or HR account. One frozenset closes both directions at once, which is what keeps them in step.
- **Admin and Super Admin share TEAM REACH and nothing else. They are two levels of administration, not one job with two names.** Both carry `sees_all_teams`, so the `teams` M2M is ignored for both and an admin is never scoped to its own teams (that was tried; an admin with no teams could open nothing). Above that they diverge, and the rule behind every difference is **an administrator may not hand out, take away, or audit authority above their own**:
  - **Granting the Super Admin, Finance or HR role** — `assignable_roles()` drops all three for an Admin. An Admin hands out Admin, Manager, User and Viewer.
  - **Editing a Super Admin's role, teams or active flag** — `can_manage_role(actor, target)`. `BaseUserForm` deletes the `role` and `teams` fields when it is False, and `_apply()` returns before touching the profile, so a hand-made POST carrying `role=user` corrects the name and leaves the role alone. Verified. Name, email and password stay editable: those are housekeeping, not authority.
  - **Deactivating anybody** — `can_deactivate_users()` is `is_superadmin`, and `require_superadmin()` guards the POST branch. Deactivation is the nearest thing to deleting a person.
  - **The activity log** — `require_superadmin()` at the top of `core.views.logs`. It audits role changes an Admin makes, so it sits one level above the people it records.
- **`is_superadmin(user)` vs `is_superadmin_account(user)`, and the difference matters.** The first asks *may this person act*, so it honours the Django `is_superuser` escape hatch. The second asks *is this account above me*, and is used on a TARGET: a staff account carrying the superuser flag is above an Admin whatever its profile role says. Using the actor helper on a target would let an Admin demote a Django superuser whose profile role happened to read `manager`.
- Two helpers, one per axis, and every screen asks both: `accessible_teams()` / `can_access_team()` / `@team_required('<slug>')` for reach, and `can_edit_data()` / `can_edit_team()` / `require_edit(user, slug)` for writing. `is_admin()` is a third, narrower question (users, settings, deleting a KPI) and is NOT the same as being able to write KPI data; `is_superadmin()` is a fourth, narrower still.
- **Deleting a KPI is ADMINISTRATORS ONLY, and a Manager is refused it** (`require_admin` at the top of the `_action == 'delete'` branch in `apps/kpi/screens.py`; the bin icon and the whole confirm modal sit inside `{% if is_admin %}`). A Manager owns their team's figures and may author, retarget and refile them. Retiring the metric takes the scorecard away from everyone reading it and every record already entered against it with it, which is a level above writing a number. Creating and editing a KPI is unchanged and still `can_edit_data`.
- **TWO of the four KPI screens are WRITERS ONLY, and that is a screen-level refusal, not a stripped-down page.** Dashboard and KPI Definitions render for anyone who reaches the team. **Import Data and KPI Management (and the CSV / workbook template downloads) are refused outright to a User or a Viewer**: every reason to open one is a reason to write, so a data-entry console and a formula authoring screen with all their controls removed are pages with nothing left on them. `access.edit_required` is the decorator, applied in `KpiScreens.__init__` via `wrap(..., writers_only=True)`, OUTSIDE the two-stage shell so a refused role never gets a page frame first. `require_edit()` inside the POST branches stays: it is what still guards the two screens a read-only role may legitimately be standing on.
- **The activity log is SUPER ADMINS ONLY** (`require_superadmin` at the top of `core.views.logs`; it was administrators generally until Admin and Super Admin split). It carries sign-ins, failed sign-ins and role changes as well as KPI edits, so it is administration rather than team data, and reaching a team's figures was never enough to read it. It also records what an **Admin** does, which is why an Admin does not read it. **A Manager writes their team's numbers and does not come here either.** Everyone still reads their own recent actions in Settings → Activity, where the "See the full log" link is behind `is_superadmin`. `activity.visible_to()` is unchanged and still scopes what is returned: it is the layer Settings goes through too.
- **Three lists have to agree about those screens, and they now share one source.** `context_processors._TEAM_SUBPAGES` / `_BRANCH_SUBPAGES` carry a `writers_only` flag per page, `team_nav(team, path, writer)` drops them, and `apps/core/search.py` passes the same `can_edit_data(user)` in. Sidebar, search palette and the view itself therefore cannot disagree, and a read-only user is never offered a link that 403s on arrival. The sidebar's Logs entry and `search.py`'s both sit inside `is_superadmin`; User Profiles stays on `is_admin`.
- Enforced in FOUR places: the sidebar (context processor `navigation` → `nav_teams`) shows only accessible teams and, within one, only the screens that role may open; each LOB view is guarded `@login_required` + `@team_required('<slug>')` (403 otherwise); **`@edit_required` refuses Import Data and KPI Management to a read-only role**; and **`require_edit()` runs at the top of every POST branch in `apps/kpi/screens.py`**. That last one is still the real read-only guard for Dashboard and KPI Definitions, which serve read and write from ONE view, so a hand-made POST has to be refused in the view. Templates read `can_edit` from the `permissions` context processor and drop the Create / Edit / Delete / Add Record / Import controls and their modals, but hiding a button is presentation, not access control. Profiles auto-created via a `post_save` signal.
- Migration `core.0008_userprofile_viewer_role` adds `viewer`. Nothing was renamed, so no profile had to move, but `role='user'` now MEANS read-only rather than "same as a manager".
- **RESTRICTED DEPARTMENTS: Finance and HR are opened by ROLE, and by one role each** (`apps/core/restricted.py`, `RESTRICTED_TEAMS = {'finance': Role.FINANCE, 'hr': Role.HR}`). Two questions in order: a **Super Admin** (or a Django superuser) reaches both; otherwise you reach the one your role names, and nobody else reaches either. **An Admin and a Viewer reach every other department and not these two.** It narrows `accessible_teams()`, never widens it, which is what makes one subtraction cover every screen at once: the sidebar, `team_required`, the dashboard's team filter, the search palette and the log's Module filter all ask that one function.
  - **This replaced a NAMED-PERSON allowlist** (`restricted_teams.json`, two hard-coded emails, matched case-insensitively, `lru_cache`d, failing safe on a malformed file). The file is deleted and so is `is_allowed` / `allowed_emails` / `reload`. **Don't reintroduce it**: who opens payroll is now answered the way every other access question is, by a role on a profile, so it is granted from the Users screen instead of by a deploy.
  - **The Django superuser flag IS honoured now**, which the allowlist deliberately refused it. The escape hatch exists so a locked out administrator can run the system, and a Super Admin is exactly who these departments are open to, so the two rules no longer disagree.
  - **Knock-on, and it is intended:** `assignable_teams()` is `accessible_teams()`, so only a Super Admin, a Finance or an HR account can assign somebody to those departments at all.
  - Adding a third restricted department is a row in `RESTRICTED_TEAMS` plus a role on `UserProfile.Role`, and nothing else.
  - **A Manager or User assigned to Finance or HR through the `teams` M2M still does not reach it.** That was true of the allowlist too and is not an oversight: the department is opened by the role, so its staff hold the Finance or HR role rather than a team assignment.
- **`apps/core/activity.py`'s scoping is unchanged and still correct, but only Super Admins reach the page now**, so in practice every reader of `/logs/` sees the whole log. Keep the scoping: it is what Settings → Activity goes through, and it is what would keep the table honest if the page were opened up again. Team entries follow `accessible_teams`; an entry with **no team** (a sign-in, a role change) is the system's own trail and needs `sees_system_entries()`; everyone always sees their own.

## Sessions — 1 hour idle sign-out (BUILT)
- **Idle, not absolute.** The clock restarts on every request, so someone entering a month of figures is never interrupted; an hour away signs them out. `SESSION_IDLE_TIMEOUT = 3600` in `config/settings/base.py`.
- **`apps/core/middleware.SessionIdleTimeoutMiddleware` is the authority, not the cookie expiry**, and that is the whole point. `SESSION_COOKIE_AGE` + `SESSION_SAVE_EVERY_REQUEST` already give a rolling window, but an expired cookie just stops existing: the next request arrives anonymous, `@login_required` bounces it, and the user gets a bare login screen with **no explanation and nothing in the activity log**. The middleware instead calls `auth.logout()`, which fires `user_logged_out` so the receiver in `signals.py` writes the audit row, then adds the flash and redirects to `?next=<where they were>`.
- **`SESSION_COOKIE_AGE` is `SESSION_IDLE_TIMEOUT + 120` on purpose.** Both enforce the same hour; the extra two minutes guarantee the server is still asked and can explain itself rather than the browser dropping the cookie first. Don't "fix" the mismatch.
- Placement matters: **after `AuthenticationMiddleware`** (it reads `request.user`) and **after `MessageMiddleware`** (it writes a message). `prod.py` rebuilds MIDDLEWARE from `_BASE_MIDDLEWARE` and splices WhiteNoise in at index 1, so anything added to base carries over.
- **Static and media paths do not count as activity.** Under `runserver` assets come through the whole stack, so a page would re-stamp the session dozens of times and, worse, an abandoned tab quietly pulling a font would hold a session open forever.
- **The message is added AFTER `auth.logout()`**, since logout flushes the session it would otherwise be stored in. Adding it after starts a fresh anonymous session to carry it.
- **`templates/partials/toasts.html` moved OUT of `{% block layout %}`** (it is still outside `<main>`). The login page replaces that block wholesale, so no Django message could ever render there. That made it the one screen the expiry notice had to reach and couldn't. It now sits with `context_menu_guard` / `loader` / `tour`, which are outside for the same reason.
- The two-stage render needed no change: `async-content.js` already checks `response.redirected` and hands over to the real login screen rather than injecting it into the page frame.
- Session data stays server-side (`SESSION_ENGINE` = db). The browser holds only the opaque key, so no role, team or KPI figure is ever readable in a cookie.

## Caching — `apps/core/cache.py` (BUILT)
- **Postgres is the source of truth; Redis is the cache, and the two never swap jobs.** Everything stored in the cache is a derived answer that can be rebuilt from Postgres, which is what makes a wiped cache a non-event: the next reader misses, recomputes from Postgres and re-stores. Nothing in Redis is the only copy of anything, so the free plan's lack of persistence costs one slow page load.
- **Three numbers, and they are not the same thing.** *Stale* (5 min) is how long a cached answer is served as-is; nothing is ever handed out past it. *GC* (30 min) is the key's TTL, and the only thing bounding the keyspace. *Invalidation* is immediate and waits for neither: a write retires its team's cache on the spot. A fourth, `CACHE_VERSION_SECONDS` (30 days), is the version tokens' TTL, long because a token must outlive every entry it stamps and finite because an unbounded key is one nothing ever reclaims.
- **Backend is `django.core.cache.backends.redis.RedisCache`** over `REDIS_URL` (`redis==8.1.0`): the `cache` Valkey container in dev, **Render Key Value** (free, 25MB) in staging, injected by `render.yaml` from a `type: keyvalue` service. **This replaced `DatabaseCache`** — every cache read was a query against the database the cache exists to spare, every write an INSERT, and the culling pass a DELETE. `manage.py createcachetable` is gone from both start scripts and migration `core.0010` drops `django_cache`. **NOT LocMemCache** either: it is per process, and staging runs several gunicorn workers, so an edit handled by worker 1 would leave workers 2 and 3 on the old figure.
- **Set the eviction policy to `allkeys-lru`**, not a `volatile-*` one (`render.yaml` and the compose command both do). Every key is a rebuildable derived answer, so the least recently used is always the safest to drop, version tokens included: losing one over-retires, which costs a recomputation, never a wrong figure.
- **Every call in `apps/core/cache.py` is fail-soft** (`_safe`): an unreachable Redis is logged once per call and treated as a miss, so the page is built from Postgres instead. Verified by stopping the container — all four screens still render and writes still succeed. An invalidation lost that way cannot strand a stale answer either, since there is no reachable cache to hold one.
- **Invalidation bumps a VERSION token that is part of the key; it never deletes keys.** One team's cached answers are spread over several keys, some carrying the dashboard filters, so the set is open-ended and cannot be enumerated. One token retires all of them, and `SCAN`ning the keyspace on every write would be O(keyspace) against a token that is one `SET`. **This is what the TTL is for**: it sweeps the orphans the bump left behind. Shortening GC to the stale time would work but would rewrite every combination still being read every five minutes.
- **The token is a timestamp, not a counter.** A counter that fell out of the cache would restart at 1 and could make retired keys reachable again; a clock-minted token is always greater than every token before it, so a lost one can only over-retire, never resurrect.
- **Invalidation is wired as model signals (`apps/kpi/signals.py`), not at call sites.** The alternative was a line in `save_record`, another in each delete branch, another in the importer, another in both KPI forms, and one more in every future screen — one would be forgotten and the symptom would be a stale figure nobody could reproduce. Signals also cover the Django admin (the only place a deleted record or import can be restored) and `seed_lob_kpis`. Soft deletes are saves, so `post_save` sees them; `post_delete` is wired too.
- `_team_of_kpi` is `lru_cache`d because a record save would otherwise cost an extra SELECT per row of an import just to find the team. Safe because **a KPI never moves between teams** — nothing offers a way to change `team`. If that ever becomes editable, this memo has to go.
- **`invalidate_team_on_commit` fires on commit, not on save.** Bumping first would let a concurrent reader recompute from the pre-commit database and store THAT under the new token, which is the one ordering that leaves a wrong answer cached as fresh.
- **What is cached:** the org dashboard's per-department row (`_department_row`, keyed on team + window + status), and per team/branch `scorecard_rows`, the definitions rows and `import_stats`. **The dashboard's global-filter combinations are cached too, not just the unfiltered view** — a filtered row costs the same to build, the window is usually one the whole company is looking at that week, and an unused combination expires on the GC clock like anything else.
- **The KPI Records / Import History tables stay UNCACHED, deliberately.** They vary by search text, page, status, source, KPI, tab and date, so the combinations are effectively unbounded and each one would be read about once. They are already `select_related` / `prefetch_related`. Revisit only if profiling says otherwise.
- **Reads are BATCHED, and that matters more against a network hop than it did against a local table.** `cache.versions()` / `cache.team_keys()` / `cache.fetch_many()` turn "N version reads plus N value reads" into two `MGET`s whatever the department count. `fetch_many` stays fully lazy: a producer runs only for a key that actually missed. Measured with `valkey-cli config resetstat`: one warm org dashboard is exactly **2 Redis commands**, and a `None` row (a department the filters emptied) is a cached answer rather than a miss, which is why `_MISS` is a sentinel and not `None`.
- **Cached per DEPARTMENT, not per page.** A department's row depends on its own data and the window, not on who is reading; caching finished pages would give every combination of accessible teams its own entry and share almost nothing.
- **A user's role or team assignment needs no cache scope.** Which cached team rows get assembled into a page is decided per request from `accessible_teams`, so a role change takes effect on the next request without touching the cache.
- `import_stats` carries **today's date in its key**: two of its tiles are worded against the current month and must not still say "August" after midnight.
- **Anything cached must return plain data.** A queryset in a cache is a snapshot pretending to be live: pickling one stores the rows.
- Measured on the dev database: the org dashboard is 28 queries cold and **8 warm** (zero `kpi_record` / `kpi_definition`), the same warm for a status filter and for a date range. A write to one team's data recomputes **that team only** (10 queries), leaving the other nine warm.
- **The category dropdown's label is `obj.name`, not `str(obj)`** (`CategoryChoiceField.label_from_instance`). `KpiCategory.__str__` is `"<team> · <name>"`, so the default label reached through `obj.team` for every option of every picker, and KPI Management renders eleven of them (the create form plus one Edit modal per row): **28 `core_team` SELECTs for one team's name, now 3.** It reads better too, since the queryset is already scoped to that team.

## Sidebar navigation (BUILT)
- Each accessible team renders as a **collapsible dropdown** (native `<details>`) of its sub-pages; a team with only one page renders as a plain link. Sub-links are data-driven: the context processor includes a page only if its URL resolves (`<slug>:index` / `:import_data` / `:kpis` / `:kpi_management`), so new per-team pages appear automatically, **and only if this role may open it** (Import Data and KPI Management carry a `writers_only` flag, so a User or a Viewer sees Dashboard and KPI Definitions alone). Operations and Nexzys = Dashboard / Import Data / KPI Definitions / KPI Management; other teams = Dashboard only.
- **Teams can split into branches** (sub-teams) — the dropdown then nests one level deeper. Convention: the LOB app exposes `NAV_BRANCHES = [(slug, name), …]` from `apps/<slug>/branches.py`, and its URLs provide `branch_index` / `branch_import_data` / `branch_kpis` / `branch_kpi_management` taking the branch slug. The context processor discovers this by import — no registry in `core` to keep in sync. A branch team's own `:index` link stays labelled **Dashboard** — it *is* one (a rollup of every branch), and the nesting already shows it sits above each branch's own. (It read "Overview" until that page grew tiles and a chart.) **TWO branch teams: Sales** (seo / leadgen / transitions) **and Operations** (seven business units, see below). VCT was briefly modelled this way too — it isn't; see the VCT/SMM/Content note below.

## Breadcrumbs (BUILT) — `context_processors.breadcrumbs` + `partials/breadcrumbs.html`
- **Its own row directly under the header, outside `<main>`.** Not inside the header: that is a fixed `h-16` whose `<h1>` already truncates, so a trail squeezed in beside it would be the first thing to vanish on a narrow screen. Not inside `<main>` either, since main is the scroll container and the trail must not scroll away from the page it labels.
- **Built from the RESOLVED URL, never from the path**, so a screen is named the way the sidebar names it rather than by title-casing a slug. `request.resolver_match` gives the namespace and the url_name; the URL namespace **is** the team slug, which is the same fact `team_required` and the sidebar already rely on, so one indexed `Team` lookup names the department without any view passing anything down.
- **A context processor, not per-view context.** Ten LOB views and four shared ones would otherwise each build the same list, **and every two-stage shell would have to build it a second time**. Being in `base.html` it arrives with the page frame and never waits on the content fetch.
- Three shapes: `Dashboard` · `Dashboard › Operations › Moxxi & Jade › Import Data` · `Dashboard › User Profiles`. **The dashboard itself renders nothing** (the partial needs more than one crumb): a trail whose single entry is the page you are looking at tells you nothing.
- **The leaf is text, never a link**, and carries `aria-current="page"`. A department's own landing page is not repeated as a leaf either, since the crumb above it already is that page (`index` / `branch_index` are skipped).
- Page labels come from `_PAGE_LABELS`, built from `_TEAM_SUBPAGES` / `_BRANCH_SUBPAGES` rather than retyped, so renaming a screen in the sidebar renames it in the breadcrumb by the same edit. Branch names come from `NAV_BRANCHES`, for the same reason.

### Two-dashboard model
- **Overall Dashboard** (`apps/dashboard`) — org-wide rollup, shared to EVERYONE, default landing on login.
- **The Overall Goal tile is GOAL PROGRESS, not average performance, and that decides both denominators.** It used to average only the departments that had reported, each over only its own KPIs that had figures, so **one KPI at 100% out of 79 lit the trophy at 100%**. Now: a department's figure is the mean over every KPI it has set a **target** for, and **a target with no figure counts as 0**; the company figure is the mean over **every scorable department**, and one that has reported nothing counts as 0. Same data today reads Sales 10.0% and the company 1.0%. Each department still counts ONCE, or Sales' 17 KPIs would outvote SMM's 3 and the number would measure who tracks the most KPIs.
- **A KPI with NO TARGET is excluded from both, and that is not the same as counting it as zero.** It has a figure but nothing to judge it by (the existing `monitored` status), so it can be neither attained nor missed. 15 of the 79 KPIs are untargeted (Site Lead 6, Sales 7, SMM 1, Content 1). Counting them as losses would also put 100% permanently out of reach for any department that owns one. For the same reason a department with **no** targeted KPI keeps `avg = None` and stays out of the company denominator: that is "cannot be scored", not "scored zero". Every department currently has at least one, so nothing is excluded today.
- **`scored_count` vs `scorable_count` vs `missing_count`.** `scorable_count` is the figure's denominator (targeted KPIs), `scored_count` the subset with a real figure, and the gap is what the coverage lines report. `focus` / `best` / `trend` stay over KPIs that actually have figures: they are about performance, and a KPI nobody has reported cannot win or lose a comparison. `org.reporting` is now only the coverage story ("who has entered anything"), no longer what the number is made of; `org.counted` is the denominator.
- **The Global Filters card is LIVE** (was front-end only). A plain GET form, no JS in the apply path, so a filtered view is a bookmarkable URL: `?period_from=&period_to=&team=<slug>&status=<key>`. Three controls only. The **Reporting Period preset dropdown and Compare To were removed**: the range picker already expresses every preset (its popover does day range / month / year), and a comparison is not a filter, since "This period vs last" already answers it. Don't reintroduce either.
- **The filters are applied inside `_department_rows()`, never to the finished rows.** Every figure on the page (Overall Goal, the cards, both charts, the movers) is derived from those tallies, so filtering afterwards would leave the percentages describing a set the reader can no longer see. `status` filters KPI by KPI and a department with no match is dropped entirely rather than drawn at 0%, which would read as failure rather than absence.
- **The period window is an OVERLAP test, not containment** (`_in_window`). A KPI's period is a span and the LOBs report on four cadences, so a week in August must reach the August monthly record AND the Q3 quarterly one. Containment would mean only a quarter-long range could ever see a quarterly KPI. The window applies to the **current** record only: its comparison partner is simply the record before it, in or out of the window, or asking for one month would kill the trend panel for every department.
- **Status values are the status KEYS** (`on_track` / `at_risk` / `below` / `monitored` / `no_data`), not the labels, so a shared URL doesn't depend on wording. `no_data` is offered even though it is not a band verdict: it is a state the cards show, and leaving it out made it the one state on the page you could not ask to see.
- **`partials/date_range_picker.html` submits `<name>_from` / `<name>_to` as ordinary hidden fields** and now takes `from_value` / `to_value` to re-open on an applied range. `date-range-picker.js` parses those by hand rather than `new Date(iso)`, which reads a bare `YYYY-MM-DD` as UTC midnight and would open the picker a day early west of Greenwich.
- **The filter form carries no `action` on purpose.** The browser then submits to the document URL, and a GET submission replaces the query string outright. Building it from `request.GET` would embed `partial=1` on the stage-2 fetch and return the bare fragment. Same trap as the KPI screens' pagers.
- **The Overall Goal modal's "By department" list is GONE, replaced by `Insights`** (`_insights()` in `apps/dashboard/views.py`). It was the Departments section printed a second time in a smaller font. A modal opened from the company figure should explain that figure, so each finding names the departments involved and says what it means for the number. Seven findings, ranked most actionable first: **Nothing reported yet · Below target · Losing ground · Reporting part way · At target · Improving · Tracked but not scored**, each emitted only when it applies. They are **grouped, not one row per department** (ten rows saying "reporting" is a list, not analysis), and names are truncated past four with "and N more". `tone` is a KEY (`good`/`warn`/`bad`/`muted`) mapped to a colour in the template, since Tailwind never scans Python. Copy avoids clauses that a status filter would falsify: "at or above 100%", not "across every target it owns".
- **The modal's whole numbers are and always were live** (`org` / `departments`), recomputed per request, and they now follow the global filters too. Its stat tiles are a fixed `h-16` with the icon panel filling that height, so the icon scales with the tile instead of floating in an oversized column.
- **Each department card also reports WHEN IT LAST REPORTED** (`_reporting_activity(team)` in `apps/dashboard/views.py`), and a department with business units lists every unit with its own figure. A rollup alone hides the branch that has not reported since June, which is the whole reason the breakdown is there.
  - **"Reported" means either way in:** a record typed on Import Data, or an uploaded workbook. Counting imports alone would show a department that types everything by hand as silent. `KpiRecord.updated_at` rather than `created_at`, because correcting last month's figure today is reporting activity.
  - **Deliberately OUTSIDE the global filters.** Those pick which reporting PERIODS are scored; this is when a person last acted. A range covering July must not make a department look abandoned because the figures it entered yesterday were for August.
  - Two grouped queries per department whatever the unit count, plus one for the unit names. Soft-deleted records and imports are excluded, so undoing an import takes its timestamp off the card with it. It rides the same per-department cache entry as the rest of the row, and the `kpi` signals already invalidate on both `KpiRecord` and `KpiImportBatch`.
  - Units sort most-recent first with the never-reported last (split into two lists, not sorted on a tuple: two `None`s would be compared to each other). The relative figure is **one unit** (`timesince(..., depth=1)`), so it reads "3 days ago" and not "3 days, 4 hours ago"; the exact stamp is on the element's `title`.
- **The donut skips departments at 0.** It divides up contribution to the company figure, and ten zero-width slices is a legend of empty names.
- **`apps/core/kpi.goal_attainment(entries)` is the ONE implementation of that roll-up**, taking `(has_target, attainment)` pairs and returning `(average, counted)`. Both the Overall Dashboard's department cards and `KpiScreens._overview()`'s branch cards call it, so a team cannot read one figure on its own page and another on the company one. Both were rewritten to average their own list before it existed, which is exactly how they drifted apart.
- **The branch overview follows the same rule** (`/sales/`): SEO read 100% off one reported KPI and now reads **25.0%** (1 of 4 targets), Lead Gen and Transitions **0.0%** instead of "No Data". A branch at 0% is now CHARTED, because that is a real reading rather than an absence; only a branch with nothing targeted sits out, and its label is **"No Target"**, not "No Data".
- **A branch's own dashboard (`/sales/seo/`, `templates/kpi/dashboard.html`) has no rolled-up percentage at all** — four count tiles, a chart of scored KPIs and per-KPI cards, each already reading "No Data" honestly. So there was nothing there to correct. If a headline figure is ever wanted on it, feed it from `goal_attainment` too rather than averaging `chart_data`.
- **Sales' company figure (10.0%) is NOT the mean of its branch figures (8.3%).** The Overall Dashboard pools Sales' 10 targeted KPIs; `/sales/` averages three branches of unequal size. Both are defensible and neither page currently shows the other's number, but they are different questions and must not be assumed equal.
- **Per-team/LOB Dashboard** — each LOB has its OWN dashboard = that team's KPI **scorecard** (Actual vs Target + status).

### Seeding a LOB's KPIs — `apps/kpi/seeding.py` + `manage.py seed_lob_kpis`
- Every LOB's `kpis.py` describes its KPIs as prose plus an Add-Record `kind`. `seeding.py` turns a `kind` into a real `expression` and its `kpi_input` rows; `manage.py seed_lob_kpis [slug ...] [--dry-run]` walks the LOBs and writes them. **Idempotent by slug** — it never updates an existing row, because by then that row is whatever the business edited it to be.
- `KINDS` maps each kind to an expression over placeholders A/B/C: `percent` `A/B*100` · `net_percent` `(A-B)/A*100` · `accuracy` `(1-abs(A-B)/B)*100` · `variance` `(A-B)/B*100` with `score_expression=abs(...)` · `average`/`ratio`/`cost` `A/B` · `difference` `A-B` · `scaled` `A/B*C` · `days` `days_between(B,A)` with DATE inputs · `count` `A`.
- **Input keys are slugged from the operand LABEL, not emitted as a/b/c** — the key becomes a CSV column header a human fills in, so `total_exits` beats `a`.
- **The prose `formula` string in `kpis.py` is NOT parsed.** It was written for humans and varies per LOB; guessing at it would produce formulas nobody checked. `formula_text` is regenerated from the expression and the labels, exactly as the create form does it.
- **Precision and unit spacing are decided in the seeder, not trusted from ten hand-written modules.** `PRECISION` gives currency and integer formats 0 decimal places, since "₱1,180.0" and "58.0 leads" both read as bugs. Unit spacing: (HR writes `' days'`, Nexzys writes `'hrs'`). A word gets a leading space, a symbol does not, and the percentage kinds get none since the format already prints `%`.
- `Frequency` aliases: Nexzys reports provisioning "Per Wave", which is not a calendar cadence. It seeds as Monthly, the closest real period that keeps the CSV template usable.
- **The `kpis.py` modules no longer render anything.** They are seed input, and the `actual` values in them are still the old placeholder numbers. Delete a module only when its team's KPIs are settled in the database.

## Staging infra — Render + Cloudflare R2 (WIRED — connection only, no data yet)
- **Supabase is GONE** (removed 2026-08-05, replaced before any data existed). Don't reintroduce `apps/core/supabase.py`, the `supabase` package, `SUPABASE_*` settings, or the `supabase_status` command.
- **Three independent channels, don't conflate them:** (1) `DATABASE_URL` = Django ORM ↔ Postgres, the source of truth (dev: Docker container · staging: **Render Postgres**); (2) `REDIS_URL` = the cache and only the cache (dev: the `cache` Valkey container · staging: **Render Key Value**), holding nothing that cannot be rebuilt from (1); (3) `R2_*` = uploaded files over the **S3 API** to **Cloudflare R2**. Dev keeps files on local disk.
- `apps/core/storage.py` — `get_client()` (`lru_cache`d), `is_configured()`, `bucket_name()`, `upload_fileobj()`, `signed_url()`, `object_exists()`, `delete_object()`, `reset_clients()`. Client is built **lazily** and imports `boto3` inside the function, so missing/unreachable creds can never block boot. `R2NotConfigured` (an `ImproperlyConfigured`) carries the fix in its message. Nothing reads or writes yet — wiring only.
- **Why boto3, not django-storages/`FileField`:** `db_schema.txt` models the pointer explicitly (`kpi_import_batch.storage_provider/_bucket/_path`), so a plain S3 client is the smaller fit.
- **R2 gotcha baked in:** botocore ≥1.36 sends a CRC32 checksum on every upload by default, which S3-compatible providers can reject — the client passes `request_checksum_calculation='when_required'` (guarded by `try/except TypeError` for older botocore). R2 has no regions: `region_name='auto'`, endpoint derived as `https://<account_id>.r2.cloudflarestorage.com`.
- Settings in `config/settings/base.py`: `R2_{ACCOUNT_ID,ACCESS_KEY_ID,SECRET_ACCESS_KEY,BUCKET,ENDPOINT_URL,REGION,TIMEOUT,SIGNED_URL_TTL,ENABLED}`. Four env vars are all that's needed; the rest have defaults.
- `config/settings/prod.py` — adds **WhiteNoise** (static files; no nginx in front of gunicorn on Render) and auto-trusts Render's `RENDER_EXTERNAL_HOSTNAME` in `ALLOWED_HOSTS` + `CSRF_TRUSTED_ORIGINS`, so a fresh deploy works before anyone types the generated URL anywhere.
- `config/settings/staging.py` — inherits prod hardening, HSTS off by default (sticky on a throwaway domain), and **refuses to start unless R2 is configured**.
- `manage.py storage_status [--ping]` (`apps/core/management/commands/`) — prints masked R2 config, which DB the ORM points at, whether the client builds, and optionally `head_bucket`s. **Not yet run against a live bucket** (no credentials issued yet).
- `render.yaml` (Blueprint: free Postgres + free **Key Value** (`allkeys-lru`, empty `ipAllowList` so it is internal-only) + Docker web service, `DATABASE_URL` and `REDIS_URL` injected, `SECRET_KEY` generated, R2 secrets `sync: false`) + `render-start.sh` (migrate → collectstatic → gunicorn). Both run **at container start**, not in the Docker build — the build has no `DATABASE_URL`. No `healthCheckPath`: `SECURE_SSL_REDIRECT` would 301 a plain-HTTP probe.
- `boto3` + `redis` in `requirements/base.txt`, `gunicorn` + `whitenoise` in `prod.txt` → **needs `docker compose up --build`**, not just a restart.
- **The bucket must stay private** — no r2.dev URL, no public custom domain. Downloads go through a Django view that re-checks team access and returns a short-lived signed URL.

## `apps/kpi` — the KPI data layer (BUILT and wired to every LOB)
- **One shared app, not one per department.** Every LOB app is a *screen* boundary (URL namespace + views), never a data boundary — all eleven had an empty `models.py`, now deleted. KPI rows are scoped by `kpi_definition.team_id` → `core_team`, which is the same key `team_required()` and the sidebar already use.

- **The core idea:** a KPI stores `expression` (a formula over named inputs) and `kpi_input` rows whose `key` is *simultaneously* the expression variable, the CSV column header, and the form field name. Adding a KPI adds zero lines of importer code.
- **`audit_log` lives in `apps/core`, not `apps/kpi`** — one deliberate deviation from the schema doc (noted there too). It records logins and user management as well, so the shared layer shouldn't depend on a feature app to write its own trail. ## One workbook per team (EVERY LOB)
- **The shape changed.** Instead of a CSV per KPI, a team downloads **one .xlsx with a sheet per KPI**. Creating a KPI adds a sheet and deleting one removes it, with no further action: the workbook is built on demand from `kpi_definition`, exactly as the CSV is and for the same §A.6 reason (a stored file goes stale the moment a formula changes).
- **All ten LOBs run it.** Operations was the pilot; `KpiScreens(workbook_template=True)` is now passed by every LOB's `views.py`, and each `urls.py` carries `manage/templates.xlsx` → `kpi_workbook`. **The route is not optional** — with the flag on and no route, `_urls()` raises `NoReverseMatch` on every screen. The flag drives BOTH the single Download-template button and the removal of the per-row CSV Template column, so a screen can never show neither or both (`per_kpi_templates` in the context).
- **A branch team gets one workbook per BRANCH, not per team** (`/sales/<branch>/manage/templates.xlsx` and `/operations/<unit>/manage/templates.xlsx` → `branch_kpi_workbook`). A KPI belongs to a branch and the four screens are branch-scoped, so the download follows the screen it sits on. `KpiScreens.url()` reverses it by prefixing `branch_`, same as the other five branch routes. The `/sales/` rollup has no button: `_overview()` builds its own context and never calls `_urls()`.
- **The per-KPI CSV endpoint still works everywhere** (`manage/<slug>/template.csv`) even though nothing links to it, so a template someone downloaded last week can still be uploaded. Verified.
- `apps/kpi/workbook.py` — `build(kpis, team, branch)`, `filename()`, `read_sheets()`. `openpyxl==3.1.5` in `requirements/base.txt`, so this **needs `docker compose up --build`**.
- **The sheet name is decoration; the `kpi=` cell is the identity.** Excel caps a tab name at 31 characters and forbids `[]:*?/\`, so names are truncated and deduplicated (`Time-to-Fill (Support/Leadership)` and `Time-to-Fill (Support Staff)` collide otherwise), and a user can rename a tab freely. Every sheet carries the same `kpi=team/[branch/]slug | template=N` note the CSV does, and that is what the importer reads.
- **Layout per sheet:** row 1 the masthead `# VINTAZK 360 · Operations · Client Retention Rate` (13pt bold), row 2 the `kpi=` identity line, row 3 formula + target + how-to, row 4 the column names (white on brand purple), row 5 the worked example, row 6 the blank row. The example's first cell starts with `#`, the same "this row is a note" convention as the CSV, so one rule strips both.
- **The note rows are INK (#040404), not grey.** They carry the KPI's identity, formula and target, which is the first thing anyone opening the tab needs to read; greying them said "skip this". The example row is ink too, so its numbers can be read and copied. What marks it as an example is the tint fill plus a trailing `← example, ignored on upload` cell one column past `remarks` (`read_sheets` zips cells against the column names, so a trailing extra is dropped, and the row is skipped as a comment anyway). A blush cell under `period` marks where to type.
- **`importer.parse_and_apply_workbook()`** writes ONE batch with `kpi=None` (which is why that column is nullable and why Recent Import History already read "Multiple"). `_collect()` / `_apply()` are shared with the CSV path, so a number in a spreadsheet is validated exactly as the same number in a .csv.
- **A sheet nobody filled in is skipped silently. This is the single most important rule of the format** — in any given month you have figures for some KPIs and not others, and being told "Actual billable hours is required" about every sheet you deliberately left alone would make one workbook worse than six CSVs. `_collect()` drops any row carrying only its period.
- **A stale or unknown sheet is an issue on that sheet, not a rejection of the file:** one KPI's formula changing must not stop the other five reporting. But if EVERY sheet fails to resolve, that is a whole-file problem (wrong team) and is raised once on the form instead of repeated per sheet.
- **Excel type quirks are flattened in `workbook._cell_text()`:** a date-formatted cell comes back as a `datetime` and would arrive as `2026-08-06 00:00:00` (rejected); a whole number comes back as `17.0` and would fail an integer input's "must be a whole number". Both are normalised before `records.coerce()` sees them.
- `kpi_import_issue` has **no sheet column**, so a workbook's issues are prefixed with the sheet name in the message (`Client Retention Rate: "n/a" is not a number`). Add a column if the issue drill-down UI ever needs to filter by sheet.
- **Portability, checked rather than assumed.** The file is a plain OOXML zip (ECMA-376 / ISO 29500) with no VBA or Excel-only parts, written by openpyxl with no Excel anywhere in the stack, so Google Sheets, LibreOffice, Numbers and WPS all handle it. Verified: a workbook re-saved by a different writer with all our styling stripped still imports.
- **Spreadsheets autocorrect the period cell, and that used to fail the upload.** Type `2026-08` in Sheets or LibreOffice and it can come back as a real date; openpyxl then hands over a datetime and `periods.parse` rejected it. `periods._ISO_DATE` now reads a full date as the period CONTAINING it, which is unambiguous at every cadence (`2026-08-06` is August monthly, Q3 quarterly, W32 weekly, 2026 annually). Genuinely wrong input (`August 2026`, `2026-13`, `2026-02-30`, `2026-Q5`) is still rejected with the same messages.
- **Gotcha:** `periods.parse`'s first parameter is `cell`, not `label` — it has to call `label()`, and a parameter of that name shadowed the function.
- **Rejected with a clear message:** `.ods`, `.xls`, a CSV exported from one tab (no `kpi=` header), and a non-spreadsheet renamed `.xlsx`.
- Uploads accept `.xlsx` or `.csv`; `KpiScreens._import_data` picks the reader off the extension. `_store()` names the object `workbook-<uuid>.xlsx` when there is no single KPI to name it after.

## Guided tour (BUILT) — `apps/core/tour.py` + `static/js/tour.js`
- **The steps are built on the SERVER, not in JS.** Which department the tour walks through is `accessible_teams(user).first()`, and whether it visits Import Data and KPI Management at all is `can_edit_data(user)`. Deciding that in the browser would mean a second copy of `apps/core/access.py`. A **user** and a **viewer** get dashboard → sidebar → their team's dashboard → KPI Definitions → done; **superadmin / admin / manager** get Import Data and KPI Management as well. A superadmin, admin or viewer reaches every team, so the tour uses the first in sidebar order, which is Operations.
- **It spans several pages**, and there is no SPA underneath: "Next" on the last step of a page is a real navigation. Progress lives in **sessionStorage** (`vintazk:tour`), and every page load asks "is a tour running, and is this the page its current step belongs to?". Wandering off mid-tour clears it rather than letting it ambush the user on a later visit.
- **`UserProfile.is_new_user`** (migration `core.0009`, default True) decides only whether it plays BY ITSELF, and only on the dashboard. `POST /tour/seen/` (`core:tour_seen`) clears it when the user finishes or skips. The header's help button replays the tour at any time and **never** changes the flag: the view only writes when the flag is still True. Re-arm someone's tour by ticking it back on in the admin (the profile inline on the User page).
- **Every step points at a `data-tour="…"` attribute**, not an id or a utility class. Restyling a panel then cannot silently break the tour, and a reader of the template can see the element is spoken for. All six hooks: `overall-goal`, `global-filters`, `dashboard-detail` (dashboard) · `north-star` (department dashboard) · `kpi-records` (import) · `manage-actions`, `kpi-definitions`. **10 steps** for a write role, 7 for a read-only one.
- **The tour is deliberately short, and stays that way.** Two rules earned by shortening it: a step per panel narrates a page the reader is already looking at, and the copy is two sentences at most. `dashboard-detail` is one step over three panels (department cards, both charts, the period comparison), the whole department dashboard is one step taken on its **North Star** banner with "the cards and charts below" pointing at the rest, Import Data is one step on the **KPI Records** section (Add Record and Import sit in that section's own header, so the table and the two ways of filling it are the same box), and **KPI Definitions has no step at all** — it is a reference page for when a figure is unclear, and it taught nothing the department dashboard had not shown.
- `dashboard-detail` also made the case that fixed the geometry below: the region is several screens tall.
- **The ring is CLAMPED and re-cut every frame**, which is what makes a long region workable. Unclamped, a target taller than the screen draws a line off the top and another off the bottom, and the card gets pushed into whatever corner is left. Clamped, the ring hugs the visible slice and follows as you scroll. A tall target opens scrolled to its TOP (`block: 'start'`), not its centre.
- **It clamps to `<main>`, not to the window**, for anything inside it: the header and the footer are chrome the highlighted panel scrolls *under*, so a ring drawn across them would claim to be highlighting them too. Tucked between them, both stay dimmed with the rest of the page. The sidebar step is what makes this a test (`main.contains(target)`) rather than a constant, since it points outside that container. The card is held inside the same frame.
- **The move between two steps is animated; following a scroll is not.** The box is rewritten every frame, so a CSS transition on it leaves the ring trailing the panel. `.tour-spotlight.is-shifting` carries the transition and `tour.js` takes it off 220ms after a step opens.
- **The page must stay scrollable, so the overlay is `pointer-events: none`.** An overlay that swallows clicks swallows the wheel with it. Clicks are blocked by a capture-phase listener in `tour.js` instead, which lets it exempt the card and still land before any link on the page.
- Card placement is below the target, above it, right, left, then the bottom-right corner. The corner is only reached by a region that fills the viewport, where overlapping is unavoidable and staying put while the reader scrolls is the thing that matters. The card also stops moving once its target scrolls out of sight, rather than sliding to the middle of the screen and back.
- **A step whose element is not on the page is SKIPPED, never fatal.** The Actual vs Target chart only renders once a KPI has been scored, so a new team has pages the tour would otherwise stall on. The step counter can therefore jump; the total is still the truth.
- **The screens render in two stages** (`apps/core/async_content.py`), so at DOMContentLoaded there is nothing to point at. The tour waits for `vintazk:content-loaded` when an unfinished `[data-async-content]` host is on the page. For the same reason the `tour` context processor sits out the `?partial=1` fetch: that response has no `base.html` in it.
- **The spotlight is ONE element, not four masking panels:** a box the size of the target with a `9999px` shadow spread, so the same shadow that outlines it dims everything else. Placement is a single `requestAnimationFrame` loop rather than scroll / resize listeners, since it has to track the element through a smooth scroll anyway.
- **Scanning for the next step must not change the page.** `present()` asks; `usable()` may open something first (the sidebar is `display:none` below md until its fragment is `:target`, so that step carries `reveal: '#sidebar'`). Only the forward scan, which lands on what it finds, is allowed the side effect. Working out whether Back should be enabled used to run the same check and slid the drawer out of nowhere.
- The header's filled info mark now **starts the tour** instead of showing one tooltip. Same symbol as the marks beside each heading, one step up in scope: those explain a panel, this explains the app.

## Header search (BUILT) — `apps/core/search.py` + `static/js/search.js`
- **The header's search box is a BUTTON, not an input.** Typing happens in the palette it opens (`templates/partials/search_palette.html`), so there is one field, not a decorative one in the header that quietly discards what you type. It is `w-56` and `lg:w-[17.5rem]` (280px, the sidebar's own width token); below `sm` there is no room for a field, so the icon alone opens the same palette.
- **The index is built on the SERVER, for the same reason the tour's steps are.** Which departments a person may open, and whether they administer accounts, is `apps/core/access.py`; a copy of that rule in JavaScript would be a second answer to a question that already has one, and the wrong copy would offer somebody a link that 403s. The endpoint is `core:search` (`/search/`), `@login_required`, returning JSON.
- **Pages come from `context_processors.team_nav`, the sidebar's own builder** (which is why `_team_nav` lost its underscore). A page is offered only if its URL resolves, so a new per-team screen becomes findable without being registered anywhere, and the sidebar and the search can never disagree about which screens exist. Branches nest as a subtitle (`Sales · SEO & Google Ads`), not a separate group.
- **A KPI result points at its team's KPI Definitions screen, never KPI Management.** Definitions is the one KPI page every role can open; sending a read-only user to Management would be a search result that raises `PermissionDenied` on arrival. For the same reason `_pages()` passes `can_edit_data(user)` into `team_nav()` (so Import Data and KPI Management drop out for a read-only role) and the **Logs entry sits inside the `is_admin` block** beside User Profiles.
- **An empty query is a real query**, returning every page the user can reach (53 for a superadmin, 7 for a one-team manager). That is what makes the palette a way to get *around* and not only a way to look something up, and the response is kept so re-opening costs nothing.
- **Every term must match, and the rank is decided by the first term against the TITLE.** So "operations import" finds one page rather than every Operations page plus every Import Data screen, and "imp" puts "Import Data" above "Operations".
- **Every keystroke aborts the request in flight** (`AbortController`). Without it a slow early response lands after a fast later one and paints results for a query the user has already typed past.
- **Results are built with the DOM API, never `innerHTML`** — a KPI is named by a person through a form.
- Keys: `Ctrl/Cmd+K` anywhere (a chord, so it is safe inside a form field), `/` only when the user is not typing (entering a KPI figure must stay possible), arrows wrap, Enter opens, Escape closes and gives focus back to the trigger.
- The highlighted row is `.search-item.is-active` in `input.css`, plain CSS not utilities: it follows both the arrow keys and the pointer, so one class the script toggles beats a hover utility plus a parallel "keyboard active" set that would have to be kept in step.
- Nothing here is cached. The page list is a few dozen `reverse()` calls and the KPI side is one indexed query, both far cheaper than the dashboard rows that are cached.

## Activity log — `/logs/` (BUILT, DB-backed)
- **`apps/core/audit.py` WRITES, `apps/core/activity.py` READS.** Both the Logs page and Settings → Activity go through `activity.py`, so an entry cannot describe itself one way in one place and another way in the other.
- **The log stores what changed as `old_values`/`new_values` JSON, not a prose message**, so the sentence is rendered at read time by `describe()`. Same reasoning as `formula_text`: store the data, render the words. Change the wording and every historical row re-reads correctly.
- **Sign-ins were never logged.** `AuditLog.Action.LOGIN`/`LOGOUT` existed since the table was built and nothing wrote them, so the log could not answer "who signed in?". `apps/core/signals.py` now has receivers on Django's `user_logged_in` / `user_logged_out` / `user_login_failed`. Added `Action.LOGIN_FAILED` (migration `core.0007`): the attempted username goes in `entity_name` since there is no user to attach. It is the only action that records something NOT happening, which is the point. `user_logged_out` fires even with no user (an anonymous POST to `/logout/`), so that case returns early.
- **Access scoping (`activity.visible_to`)** mirrors `apps/core/access.py` with two additions only a log needs: an entry with **no team** (a sign-in, a role change) is system-wide and only admins see it, and **everyone always sees their own entries** whatever team they touched. Verified: superadmin 11, an HR user 6, a Finance user 1 (just their own login).
- **The Module column is not a database column.** It is `team.name`, or the area name for actions that are not about a team's data (`Authentication`, `Access Control`, `System`). That makes the Module **filter** two filters in one coat: a team name filters on `team`, a system name filters on `action` (`activity.actions_for_modules`). The dropdown only offers teams the viewer can see, since offering one whose rows are all hidden is a filter that silently returns nothing.
- **Status is derived, not stored:** `target_changed` / `formula_changed` are `warning` (they rewrite how every existing figure already read), an `imported` row with `new_values['errors']` is `warning`, `login_failed` is `failed`, everything else `success`. **`deleted` is a SUCCESS, not a warning:** the column reports how the action went, not how alarming it sounds, a delete that was asked for and carried out succeeded, and every delete here is soft anyway. The Action column already says "Deleted". The template's third pill state is real now rather than dead markup.
- **`_QUIET_FIELDS` keeps the Details line a summary, not a dump:** `expression`/`formula_text`/`inputs` (long, and the Action column already says a formula moved), `slug`/`kpi` (restate the entity), `is_active` ("Deleted" is the Action; "is active True → False" repeats it). A newly-set field whose value equals the entity name is dropped too, or a create reads "Temp Probe: name Temp Probe". Past three fields it truncates with "and N more".
- **`entity_name` carries the team prefix** because `KpiDefinition.__str__` is "Human Resources · Monthly Attrition". `_short_name()` strips it when it duplicates the Module column.
- Search / date / module / action filters are plain GET in **one form** (same trap as KPI Management: two forms and applying a filter wipes the search). `PAGE_SIZE = 20`, elided page range, `anchor="activity-log"`, scrollable body with a sticky header. A bad `?date=` shows a message rather than 500ing.
- **Settings → Activity** is this account's own last 20 entries (`MY_ACTIVITY_LIMIT`), with a link through to the full log. No `visible_to` needed there: your own actions are yours to read.

## User Profiles — `/users/` (BUILT)
- **Account administration for Super Admins and Admins**, sidebar entry "User Profiles" gated on `{% if is_admin %}`. `apps/core/views.py:users` + `apps/core/forms.py` + `core/users.html` + `partials/team_checkboxes.html`. Create an account, edit name / email / role / teams, set a password without knowing the old one, deactivate and reactivate.
- **`access.manageable_users()` is every account, for both roles that reach this screen.** Administration is org-wide, so a Super Admin and an Admin administer the same set. A Manager is refused the screen outright: `is_admin` gates it, NOT `can_edit_data`, and both the GET and every POST branch go through `require_user_admin()`. `assignable_teams()` is `accessible_teams()`, so it is every team **minus the restricted departments** unless the actor is on that allowlist. `is_scoped` on the users page is a constant False (there is no team scoping left to report), and reintroducing a scoped Admin means putting `manageable_users`, `assignable_roles` and `assignable_teams` back together, not one of them.
- **The ESCALATION GUARDS are back, and they are about the role ladder rather than about teams** (they were removed when Admin stopped being team-scoped, which was the wrong lesson to draw). An Admin cannot grant Super Admin, Finance or HR (`assignable_roles`), cannot edit the role, teams or active flag of an account holding one of those three (`can_manage_role` → the form drops both fields), and cannot deactivate anybody at all (`require_superadmin` in the POST branch). Rows carry `can_manage_role` / `can_deactivate` so the buttons match what the view will accept, and an Admin looking at such an account sees a note where the Role and Teams block would be. See the Auth section above for the full ladder.
- **Nobody edits their own role, teams, or active flag here.** `BaseUserForm` deletes the `role` and `teams` fields when the target is the actor, and deactivate refuses self. An admin who demotes themselves by accident cannot undo it, because the screen that would undo it is the one they just lost.
- **Your own password IS changeable here** (it used to be refused with a pointer to Settings). One form covers both cases, because the difference is one field and one flash message, not a different screen: `AdminPasswordForm` takes an `actor`, and when it is the target it adds a **Current password** field ordered first (`order_fields`) and sets `is_self`. An administrator setting somebody else's password cannot be expected to know the old one; a session left open on your own account must not be enough to re-key it. The view then calls **`update_session_auth_hash`** for the self case, which is what stops the change signing you out mid-action, and audits it as "changed by the account holder" rather than "reset by an administrator". Settings → Account still works and is unchanged.
- **Employee ID (`username`) is not editable.** It is the sign-in credential and the `entity_name` on every audit row, so renaming it would rewrite how the log reads. Creation refuses a duplicate **case-insensitively**, since two IDs differing only in case are indistinguishable in a table.
- **A user is two rows, so the forms are plain `Form`s, not a `ModelForm`.** `User` holds the ID / name / email / active flag and `UserProfile` the role and teams; a ModelForm would own one and leave the other to be patched in the view, which is where the two drift apart. `_apply()` writes both. The profile is fetched with `get_or_create`, not created: the `post_save` signal already made one.
- **Deactivation is the only "delete" there is, and it is `User.is_active`.** Nothing is removed, the name stays on every record and log entry, and the account can be turned back on. The confirm button is armed by the shared 5s `confirm-timer.js` ring, same as deleting a KPI or a record. Reactivating is not destructive, so it has no timer.
- **Audit entries carry `team=None`**, so they are the system's own trail and follow `sees_system_entries` rather than team reach. `activity` already filed `entity_type='user'` under the **Access Control** module, so nothing there needed changing. `_snapshot()` re-reads the profile from the DB rather than off `user.profile`: the form saves through its own instance, so the cached one is the *before* state and the diff would come out empty. `_changed()` logs only the fields that moved, so the Details line reads "role Manager → User, teams Operations → Human Resources" rather than the whole account every time.
- **Gotcha, and it was live on the Logs pager too:** `_query_without_page` / `_params_without_page` rebuilt links from `request.GET`, which on the stage-2 fetch carries `partial=1`. Clicking page 2 returned the bare fragment. Both now start from `_link_params(request)`, which strips it. Same trap the KPI screens hit; anything new that builds a URL from `request.GET` on a two-stage screen starts there.

It is **popped** by the next render, which is the content stage: the shell returns long before that line. The audit entry deliberately carries no password, since the log is permanent and this is not.

It used to turn it on for every account made here, so an administrator who filled all three in was still met by "Welcome to Vintazk 360" asking for a name and an email the system already had. **The basis is what is MISSING, never whether the account has signed in before**: those are two different questions, and using the second one showed the card to every new account however completely it had been set up.

Being in the content block also means it arrives with stage 2, like everything else on that page.

When it IS changed the view calls `update_session_auth_hash`, or the first thing they did after signing in would sign them out.

Walking someone around the app underneath a form they still have to fill in is two things talking at once. Setup saves, redirects, and the tour plays on the render after that. The card is `z-[90]`, above the tour's 80/81/82, so the stacking still says which is in charge if they ever do coincide.

- **`nulls_distinct=False`** on `kpi_definition`'s unique (team, branch, slug) — without it Postgres treats each NULL branch as unique and two *team-level* KPIs could share a slug. Needs PG 15+ (dev is 16, Render is 16).
- Targets are **always bands**: a single target is a band of width zero, `target_min`/`target_max` both NULL = `monitored` ("No Target"). Same rule the shared kit already uses in `apps/core/kpi.py`.
- `apps/core/kpi.py` (the attainment/status math) **has NOT moved** to `apps/kpi/scoring.py` yet — 7 LOBs import it and it works. Move it when the views switch to querysets (rollout step 5).
- Admin registers everything; the two history tables + import issues are read-only there, since they're append-only records.
- **`apps/kpi/formula.py` — BUILT.** The AST-whitelist parser/validator/renderer/evaluator (**never `eval()`**). Grammar: input keys, numeric constants, `+ - * /`, parens, and `abs/min/max/round/days_between`. Four entry points: `parse()`, `names()`, `validate(expression, keys)` (rejects unknown names, unreferenced inputs, formulas of pure numbers, and dry-runs against a sample row), `render_text(expression, labels)` → the `formula_text` sentence, `evaluate(expression, values)`. `days_between(a, b)` = `(b - a).days`. Gotcha handled: a called function is an `ast.Name` too, so `names()` excludes `Call.func` or `days_between` reads as a missing input.
- **`apps/kpi/csv_template.py` — BUILT.** Generates a KPI's CSV template (§D) from its own `kpi_input` rows in `position` order — `build(kpi)`, `columns(kpi)`, `filename(kpi)`, `period_label(frequency)`. **Generated on demand, never stored:** §A.6 requires a fresh download to carry the *current* `template_version`, so a file saved at creation time would go stale the moment a formula changed and the importer would reject the very template the screen handed out. Period formats: monthly `2026-07`, quarterly `2026-Q3`, weekly `2026-W32`, daily ISO, annually `2026`. One deliberate refinement of §D: `generated=` is a full ISO **timestamp**, not a bare date — `kpi_import_batch.template_generated_at` is timestamptz and two downloads on the same day must be distinguishable. The three comment lines are exactly three, as the file's own first line promises. The sample row is **blank** apart from the period, so nobody uploads a demo number as real data.
- **`apps/kpi/periods.py` — BUILT.** Period labels both ways, per §D: `parse(label, frequency)` → `(period_start, period_end)`, `label(start, frequency)`, `current(frequency)`, plus `FORMAT_HINT` for error messages. Formats: daily `2026-07-15` · weekly `2026-W32` · monthly `2026-07` · quarterly `2026-Q3` · annually `2026`. `kpi_record` stores the start/end pair, not the label, because `(kpi, period_start)` is what makes a re-upload update the month instead of duplicating it.
- **`apps/kpi/records.py` — BUILT.** `save_record()` is the ONE path from raw operands to a scored record, used by **both** manual entry and CSV import, so the same numbers are stored and scored identically either way. Does: coerce per `data_type` (tolerates `1,234`, `₱`, `%`) → evaluate the expression → apply `accumulation` → score via `apps.core.kpi` (not a second copy of the band math) → upsert `kpi_record` → **replace** `kpi_record_input`. Known limit: inserting an *earlier* period on a cumulative KPI leaves later periods stale until re-saved.
- **`apps/kpi/importer.py` — BUILT.** The whole §D pipeline. `parse_and_apply(raw, team=, user=, file_name=)` → a `Result`. Whole-file problems raise `ImportError_` (nothing written, error goes on the form); per-row problems become `kpi_import_issue` rows and the batch goes `partial`. Rejects a stale `template=` (§A.6 rule 3) and a file belonging to another team. **Zero KPI-specific code** — columns come from `kpi_input`, maths from `expression`.
- **Storage gotcha:** the object key is a **UUID**, matching §9's example path, *not* a timestamp+content hash. Re-uploading a corrected file is a supported action (§F idempotency), so two uploads of identical bytes in the same second must not collide on `(storage_provider, storage_bucket, storage_path)`. `file_hash` is what spots an accidental duplicate; it surfaces as a note in the flash, not a rejection. Dev has no R2 credentials, so files land under `MEDIA_ROOT/kpi-imports/` with `storage_provider='local'`; R2 is used automatically once `storage.is_configured()`.
- **Import Data's KPI Records table has the same search + filter as KPI Management**, in the same shared template, so every LOB got it at once. Facets: **KPI / Category / Status / Source**, laid out as a **2x2 grid** rather than four columns, because KPI names are long and would truncate to uselessness in a quarter-width column. Search matches the **KPI name and the record's remarks**, the only free-text in that table.
- **The KPI facet lists soft-deleted KPIs too, labelled "(deleted)".** `kpi_record` rows survive a soft delete and still list in this table, so a facet built from `is_active=True` alone would show rows that nothing could filter to. The queryset is `Q(is_active=True) | Q(records__isnull=False)`, and the label says which is which or the list reads as though the KPI were back. Values are **slugs**, not pks, so a filtered URL survives being bookmarked or shared.
- **The Status facet filters the STORED `kpi_record.status`** — deliberately the opposite of the dashboard, which recomputes. The dashboard must not show a verdict from a target that has since moved; this table prints the stored badge, so the filter and the badge have to read the same column or a row could match "Below Target" while displaying "On Track".
- **The Add-Record and Import redirects go through `_back_to_records()`**, which rebuilds the URL from `request.GET`. A bare `redirect(request.path)` reset the filters underneath the user, and it still needs the `#kpi-records` fragment for the RFC 7231 §7.1.2 reason every `:target` modal does.
- Source offers all three of `manual` / `import` / `api` even though nothing writes `api` yet, matching how the Frequency facet offers every choice. The empty state branches on `has_any_filter`, so "no records yet" and "nothing matches these filters" give different ways out.
### Editing a record — correcting the operands, not re-entering the row
- **`EditRecordForm` (`apps/kpi/forms.py`) + the `edit-record` branch in `_import_data`.** A pencil beside the eye on every KPI Records row, and an Edit link in the View modal's footer, both behind `can_edit`. It rewrites the raw operands and the remarks; `records.save_record()` recomputes the value, the attainment and the status, so a typed correction is scored by exactly the code that scores an uploaded one.
- **The KPI and the period are NOT editable, and that is the design.** `(kpi, period_start)` is the record's identity and the key every upsert in the import pipeline turns on. Moving a record to another period would mean deleting the row underneath the user and deciding what happens when the destination is already taken, which is a different action wearing this one's clothes. A figure filed against the wrong period is still delete plus re-enter, which is what the soft delete was built for.
- **Editing sets `source='manual'` and clears `import_batch`.** After a hand correction the figure is no longer what the file said. It also keeps "delete this import" honest: that branch removes the records the batch is still the source of, and an edited one no longer is.
- **The operand fields are declared for real, unlike `AddRecordForm`'s.** There is exactly one KPI in play, so there is no need for the one-panel-per-KPI-all-disabled trick. Each form is **prefixed with its record's pk** (`record<pk>-input__<key>`), because the screen renders one modal per row and every field name would otherwise repeat down the page. `operand_fields` is a property, since declared fields come first on a Django form and iterating the form itself would put Remarks above the figures it is a remark about.
- Fields are `required=False` on purpose: emptiness is `records.coerce()`'s question, so a blank cell gets the KPI's own message ("Total exits is required") rather than the browser's generic one, and an optional input still counts as 0.
- **The POST branches CHAIN from `edit-record` onward** (`elif`), because the last of them is the fall-through for Add Record. Left as separate `if`s, an edit that failed validation dropped through and was re-read as a new record.
- Guards, all verified: a read-only role gets no pencil, no modal and a 403 on the POST; a junk or foreign pk is a 404 (`_posted_pk` + the team/branch scope); a bad cell re-renders with `!flex` forcing the modal open and the message beside the field. `records_qs` gained `prefetch_related('kpi__inputs')` so a page of ten modals costs no extra query.

### Deleting a record — soft, timed, and revivable (`kpi.0002`)
- **Why it exists:** re-uploading a corrected file fixes a wrong NUMBER, because the upsert key is `(kpi, period_start)`. It cannot fix a wrong PERIOD: the corrected file writes the right period and the mistaken row stays, dragging the dashboard, chart and tallies down with nothing in the UI able to remove it.
- **`kpi_record.is_active`** (migration `kpi.0002`), soft like `kpi_definition` (design principle 7). The row leaves every table, tile and chart; the value, its `kpi_record_input` operands and the import batch it came from all survive. Audited as `deleted` with the KPI, period and value in `new_values`.
- **Re-entering a deleted period REVIVES the row**, it does not fail and does not duplicate. The unique constraint on `(kpi, period_start)` still counts deleted rows, so `update_or_create` lands on the soft-deleted one; `save_record()` therefore sets `is_active=True` in its defaults. Without that line an upload would report "1 updated" and show nothing, which reads as data loss. Verified: same pk, one row, new value.
- **Four read sites had to honour the flag**, and missing any one of them leaves a deleted row visible: `_latest_records()` (dashboard + branch overview), `import_stats()` (the tiles), the records table queryset, and `save_record()`'s cumulative `previous` lookup. The KPI filter facet uses `records__is_active=True` for the same reason.
- **The confirm button is armed by a 5s timer, and the countdown IS the button's border** (`data-delete-timer` / `data-delete-seconds` / `data-delete-ring`). An absolutely-positioned SVG `<rect>` traces the button's perimeter; `pathLength="100"` normalises that perimeter to 100 units, so `strokeDashoffset` is a straight percentage and the outline unwinds at an even speed around the rounded corners instead of racing them. Offset runs 0 (whole ring) to 100 (nothing) and hits 100 exactly as the button unlocks. The `<svg>` needs `overflow-visible`, since a 2px stroke on a 100%/100% rect sits half outside the box.
- ONE clock, the same principle as the toast countdown: a single `requestAnimationFrame` loop drives the ring, the `(5)` in the button's label and the `disabled` state off one timestamp, so the count can never read 0 while the button is still locked. Both the ring and the count vanish at zero, leaving a plain live button.
- **The ring is `text-slate-300`, matching the DISABLED button fill** (`disabled:bg-slate-300`), not the rose `status-bad`. It is a wait indicator, not an alarm, and the button underneath is muted while it runs.
- **The sweep starts at the button's END edge, and that phase is measured, not guessed.** An SVG rect path begins at the top-left corner and runs clockwise, so the gap would otherwise open in the wrong place. `endEdgePhase()` computes the right-hand edge's position along the perimeter from the button's own `getBoundingClientRect()` (flat top + one corner arc + half the side, over the whole perimeter — about 44% on the rendered button) and offsets the dash by it. Animating `stroke-dasharray` as `drawn (100 - drawn)` with `stroke-dashoffset = drawn - phase` keeps the arc ENDING at that edge, so the gap opens there and eats round clockwise.
- The count sits at the END of the button label and the button is right-aligned in its row, so dropping it at zero moves only the button's left edge, never the one under the pointer. It is prefixed with a non-breaking space so it can never wrap onto its own line.
- **The button ships ENABLED and JS disables it on open.** If the page script never runs the guard is lost but deleting still works; a permanently dead button would be worse. Re-opening a modal re-arms it, since `sync()` runs on `hashchange`.
- **The modals live outside the table** (a `<div>` is invalid inside `<tbody>`), keyed `#recordDelete-<pk>`, exactly like KPI Management's per-row modals.
- Scoped by `get_object_or_404(..., kpi__team=team, kpi__branch=branch, is_active=True)`, so a guessed id from another LOB or another Sales branch is a 404, not a delete. Verified for both, and for double-deleting.
- **Admin lists and filters `is_active`** — it is the only place a deleted record can be restored without re-entering its period.
- **Import Data is fully wired** (all nine LOBs): live stat cards, live KPI Records table (paginated 10/page, elided page range, scroll container with a `sticky top-0` header, pager hidden when there is only one page), live Recent Import History, a working **Add Record** modal and an **Import CSV** modal. The Add-Record modal renders **one operand field-group per KPI, all `disabled` except the selected one** — disabled inputs aren't submitted, so two KPIs both using an input key like `a` can't collide. Both modals use the `!flex` + real-anchor redirect pattern (`#kpi-records`).
- **KPI Records and Import History are ONE card, two tabs** (`#kpi-records`, the same section id and the same `data-tour` hook as before). They are two views of the same data, and two stacked cards made the history read as a separate feature rather than the receipt for the table above it. **The tabs are real links carrying `?tab=imports`**, not JS-only buttons: they work with the script blocked, the choice survives a form post (the forms carry no `action`, so they post to the current URL with its query string), and `_back_to_records()` therefore lands a delete back on the tab it was made from. The JS only spares the reload, and it rewrites the URL with `replaceState` so the form action stays in step. Active styling hangs off **`aria-selected`** and Tailwind's `aria-selected:*` variants, so the script toggles one attribute and never builds a class name (which Tailwind would purge). Records is the default, so `?tab=` only ever appears for the other one and a typo'd value falls back to Records. The tab bar **wraps rather than scrolls**: `overflow-x-auto` would clip the `-mb-px` the tabs sit on, since an auto `overflow-x` forces `overflow-y` to auto too, and the underline is the whole point of the control.
- **Import History is paginated, not capped at ten** (`IMPORTS_PAGE_SIZE = 10`, elided range, same `#kpi-records` anchor). An import is the receipt for a figure someone is querying, and "which upload put this number here?" stops being answerable once the file scrolls off a fixed list. **Its pager key is `ipage`, not `page`** (`IMPORTS_PAGE_PARAM`, passed to the partial as `param`), because both tables now live on one screen and a shared key would move them together. `_query_without_page()` / `_params_without_page()` take the key so each pager drops only its OWN parameter, and both keep the tab and the record filters. The tab badge counts `import_count`, the whole set, not the page.
- **GOTCHA, and it was live: `partial=1` must never reach a link the user clicks.** These screens render in two stages, so on the fetch that builds the content `request.GET` carries that flag, and every pager pill, tab link and redirect was being built from it. Clicking page 2 returned the **fragment**: no sidebar, no header, no page frame. Reproduced, then fixed at the source. `_link_params(request)` strips `async_content.PARTIAL_PARAM` and is now the single basis for `_query_without_page`, `_params_without_page`, `_tab_url`, `_back_to_records` and `_back_to_page`. This bit KPI Management's pager too, not just Import Data. Anything new that builds a URL from `request.GET` on a two-stage screen has to start there.
- **Both tables carry a View (eye) and, for a writer, a Delete (bin) action, icon-only and borderless.** A row of outlined buttons competed with the figures. The **Actions column on KPI Records renders for every role** because viewing is a read action; only Delete is behind `can_edit`. Same treatment on KPI Management's Edit / Delete.
- **The View modals cost no query.** `record_rows()` and `import_rows()` carry the modal's detail alongside the table's columns, off rows already fetched (`prefetch_related('input_values__input')` and `('issues', 'records')`). A record's modal shows the **formula plus every raw operand** from `kpi_record_input` in CSV column order, which is the whole answer to "why is this figure what it is?". An import's modal shows the four counts and **every `kpi_import_issue`** with its spreadsheet row number, column, raw value and reason, tagged Skipped or Applied by severity: the count in the table is useless without being able to read which rows and why.
- **Deleting an import is soft, and it takes its records with it** (`kpi_import_batch.is_active`, migration `kpi.0004`). An import is one act, so undoing it row by row would leave the batch claiming records that are gone. Both sides keep everything: counts, issues, operands, and the stored file. **Only records the batch is still the source of** are removed, so a period re-uploaded later (whose `import_batch` now points at that later batch) is correctly left alone. `import_stats`' last-import tile and the duplicate-file check both filter `is_active=True`, so uploading the file again to undo the delete is not reported as an accidental repeat. Admin lists and filters `is_active`, the only place a deleted import can be restored.
- **`_posted_pk()` guards every id a modal posts.** A hand-made POST carrying `''` or `'abc'` reaches a pk lookup as a `ValueError`, which is a 500 where a 404 belongs. It returns 0 for anything non-numeric, which never matches. Verified 404 for empty, junk, unknown and another team's batch; 403 for a read-only role.
- **No client-side calculation in the Add-Record modal, on purpose.** Formulas are now arbitrary expressions, so a JS preview would mean a second evaluator that can disagree with `apps/kpi/formula.py`. The modal shows the formula and target; the computed value comes back in the flash and the table. A JS evaluator over the same grammar is the follow-up if the live preview is wanted back.
- **Verified against §F:** manual entry, template download → fill → upload (2 created), re-upload (0 created / 2 updated, still 2 records), one bad cell (`partial`, 1 issue naming row/column/value), stale template rejected, wrong-team file rejected, bad period rejected, division by zero caught on the form, and `aggregation=none` with two rows for one period rejected with a message that names the fix.
- **Not built yet:** the preset library data migration (`kpi.0002`), XLSX import (CSV only — open question 4), a download view for stored import files, the agent-level weighted scorecard, and a "Download all templates" zip (§D).

### Operations Create-KPI form — the reference implementation (BUILT, writes to the DB)
- `apps/operations/forms.py` `CreateKpiForm` + `apps/operations/views.py:kpi_management` + `templates/operations/create_kpi_modal.html` + `static/js/formula_builder.js`. **This is the pattern to copy into the other LOBs** — don't re-derive it.
- **The inputs travel with the formula.** The JS builder serialises its operands into a hidden `inputs_json` field (`[{key, label}]`, canvas order); `clean_inputs_json()` checks them against `KEY_VALIDATOR` and `save()` writes the `KpiInput` rows. Without this a KPI has no CSV columns and no Add-Record fields — the single most important thing to get right when porting.
- One `save()` writes, atomically: the `KpiDefinition` (+ generated `formula_text`, unique slug), its `KpiInput` rows, and the seed `KpiFormulaHistory` row (`reason='Initial formula'`, `template_version=1`). The view then writes the `created`/`kpi_definition` audit entry — it holds the request, the form doesn't.
- **Slugs are made unique per team** (`-2`, `-3`) — `(team, branch, slug)` with `nulls_distinct=False` otherwise 500s the second time a KPI name is reused.
- **Targets: fill one side, get both.** A single figure is a band of width zero; both empty = `monitored`. Enforced in `clean()`.
- **Categories are team-scoped** — the `category` queryset is filtered to the team, plus a `new_category` free-text box that `get_or_create`s one, since `kpi_category` starts empty and an empty dropdown is unusable.
- **Gotcha — the modal is CSS `:target`, so a validation failure would re-render it CLOSED** with the errors invisible. The view sets `open_create_modal` and the overlay adds `!flex` (beats `hidden`'s `display:none`). Errors render via `templates/partials/field_errors.html`.
- JS `VARIABLE_PATTERN` must stay `^[a-z][a-z0-9_]*$` — the same shape as `KEY_VALIDATOR`. The builder also refuses to submit an input that the formula never uses.
- **Builder limitation:** the token canvas has no way to express a function call, so the preset list drops "Days between" and "Forecast accuracy" from `db_schema.txt` §A.4. `formula.py` accepts both — only the UI can't compose them yet.
- **One queryset (`KpiScreens.queryset`) and one row builder (`KpiScreens.row`) feed all four screens**, so no two of them can disagree about a target or a formula. `management_rows()` layers `csv_url` + the per-row `EditKpiForm` on top. The **CSV Template column** links to `<ns>:kpi_template` (`/<lob>/manage/<slug>/template.csv`), behind the same `@login_required` + `@team_required` guard as every other page.
- **Every LOB's `kpis.py` is seed data only** — no view or template reads one. The per-LOB `_attainment` / `_status` / `_STATUS_LABEL` copies are gone everywhere except `apps/sales/views.py`.
- **Dashboard (`:index`) is DB-backed**, from `_scorecard_rows()`: one card per live KPI, showing its **latest** `kpi_record` (`_latest_records()` = one query, newest first, `setdefault` per KPI).
- **Five card states, and two of them are not the same thing.** `monitored` = there is a number but no target to judge it by; `no_data` = nobody has entered a figure yet (card shows an empty state and a link to Import Data). Collapsing them would report an untracked KPI as merely untargeted. Only KPIs with an attainment are charted, and a note under the chart says how many were left out and why.
- **The dashboard RECOMPUTES attainment; it does not read `kpi_record.attainment`.** The stored score is a snapshot of the target in force when the row was written, so moving a target would otherwise leave the old verdict on screen until every record happened to be re-saved. Design principle 6: scores are cached, never authoritative. Verified: retargeting Attrition 3.5 → 2.0 flipped the card from 110.8% On Track to 63.3% Below with the record untouched.
- Each card carries its **frequency and period** (`Monthly · 2026-08`, `Quarterly · 2026-Q3`), and so does the chart tooltip. Without it the cards look like one reporting period when they are not.
- `manage.py seed_operations_kpis` was **replaced** by the LOB-wide `manage.py seed_lob_kpis` (see the seeding section above).
- **The Edit modal is live and carries the full formula builder** (`EditKpiForm`). Everything is editable except the `slug` — a downloaded CSV binds to it, so renaming the KPI is fine but its address is stable.
- **Three shared partials, use them for every LOB:** `partials/formula_builder.html` (takes `form` + a `uid` unique per instance on the page — it namespaces the `_formula_mode_<uid>` radios and the preset `<select>` id), `partials/category_picker.html`, `partials/field_errors.html`. `static/js/formula_builder.js` initialises **every** `[data-formula-builder]` on the page, so the `<script>` tag belongs in the page's `{% block scripts %}` **once** — not in a partial, or it executes per copy and double-binds listeners.
- **`BaseKpiForm` holds everything create and edit agree on**; `expression` + `inputs_json` are shared fields, so the builder works in both. The two subclasses differ only in consequence.
- **What a formula edit costs (§A.6), all in `EditKpiForm`:** changing `expression` **or the input key set** (add/remove/rename/reorder) bumps `template_version`, appends a `KpiFormulaHistory` row, and audits `formula_changed`. Rewording an operand's **label** is cosmetic — it regenerates `formula_text` but bumps nothing. Three separate properties keep these apart: `formula_changed` (keys+expression), `inputs_changed` (any input edit, labels included — so a relabel isn't misreported as "Nothing changed"), `targets_changed`.
- **`clean()` blocks removing an input that already has `KpiRecordInput` rows** — `KpiInput` is `on_delete=PROTECT`, so without the check `save()` would die on a `ProtectedError` mid-transaction. `_sync_inputs()` then does add/update/remove rather than delete-and-recreate.
- **Formula/target history rows record the formula or target in force FROM `effective_from`** — the *new* value, matching §12's and §11's column docs and §E.3's seed row. §A.6's prose ("preserve the previous") is satisfied because the previous one is the earlier row; storing the old value in the new row would duplicate the seed row.
- **Moving a target appends a `KpiTargetHistory` row** and audits `target_changed`; a formula change audits `formula_changed`; an edit doing both writes **both** rows. Anything else audits `updated`; changing nothing writes nothing. `change_reason` feeds both history tables' `reason`.
- **Category picker: one control, not two.** `CategorySelect` appends a `__new__` sentinel option ("+ Create new category…"); `CategoryChoiceField.to_python` maps it to `None` so it isn't a validation error, and `clean()` insists `new_category` is then filled. The text box is revealed by **CSS only** — `.category-picker:has(select option[value="__new__"]:checked)` in `static/src/input.css`, same no-JS spirit as the `:target` modals. On a failed POST the raw `__new__` stays selected, so the box stays open.
- **Delete is a SOFT delete** — `is_active=False`, audited as `deleted`, behind a `#kpiDelete-<slug>`. The KPI leaves the table and its `template.csv` starts 404ing (both querysets filter `is_active=True`), while records, history and audit rows survive. Design principle 7.
- **Gotcha — decimal comparison.** The DB returns `Decimal('3.5000')` where the form cleans `Decimal('3.5')`. `EditKpiForm._display()` normalises with `format(value.normalize(), 'f')`; without it every description edit would look like a target change and write a spurious history row.
- **One view, three modals.** Each form posts `_action` (`edit` / `delete`, absent means create) + `_slug` + `_page` to `kpi_management`, so the create form isn't bound to an edit's POST data. `open_create_modal` / `open_edit_slug` force the right modal back open on failure via `!flex`. Modal ids are `#kpiEdit-<slug>` / `#kpiDelete-<slug>`, not loop counters.
- **Gotcha, and it bites any `:target` modal that posts:** a browser **reattaches the request's fragment to a redirect whose `Location` has none of its own** (RFC 7231 §7.1.2). A successful save from `#kpiEdit-csat` therefore redirected to a fragment-less URL, the browser put `#kpiEdit-csat` back, and the modal sprang open again on the fresh page, looking like the save had failed. Fix: every success redirect goes through `_back_to_page()`, which appends the real anchor `#kpi-definitions` (the id on the table `<section>`). Give the Location its own fragment or the old one wins.
- **Search + filters are live on KPI Management** (GET, no JS). The two inert `<select>`s were replaced by **one Filter button** opening a `<details>` popover: two columns of checkboxes (Category, Frequency), multi-select, with Clear all / Apply. The button turns brand-coloured and shows a count badge when any filter is applied (`active_filter_count`; search is excluded since it has its own visible box). Search matches `name`, `formula_text` and `expression`.
- **The search box and the popover live in ONE `<form method="get">`** so applying a filter can't wipe an active search, or vice versa. Three related traps, all handled: pagination links and the "Go to page" form now carry the filters (`extra_query` / `extra_params`, new optional params on `partials/pagination.html`); `_back_to_page()` rebuilds the redirect from `request.GET` so saving a KPI returns to the same filtered view (a form with no `action` posts to the current URL, query string included); and the table's empty state branches on `has_any_filter`, because "nothing here yet" and "nothing matches" need different ways out.
- **`partials/pagination.html` takes an `anchor`** (a section id, no `#`). Without it a pager link is `?page=2` with no fragment, so the next page loads scrolled to the **top** and the table you were reading is off-screen, which reads as "pagination is broken". Both Operations tables pass one (`kpi-definitions` / `kpi-records`). The "Go to page" box is a GET form and browsers cannot attach a fragment to one, so only the pills anchor. The partial also accepts `page_numbers` for an elided range: pass `list(paginator.get_elided_page_range(...))`, never the generator, since it is single-use and anything reading the context after render finds it empty.
- **Pagination is live** — `PAGE_SIZE = 10`, `Paginator` + `page_obj` into the existing `partials/pagination.html` (which already supported a live page object). Only the current page builds `EditKpiForm`s. `kpi_count` on the stat card is the whole set, not the page. The table body scrolls (`max-h-[34rem] overflow-auto`) with a `sticky top-0` header.
- **Templates audited across all 79 KPIs** (structure + a fill-and-upload round trip per shape): BOM present, exactly three comment lines, header round-trips through `importer.read_header` with the right team/branch/slug/version, columns are `period` + every input key in `position` order + `remarks`, the sample period parses for the KPI's cadence, and its operand cells are blank. Verified `percent`, `scaled` (3 columns), `variance` (signed display, graded on magnitude), `count`, `cost` (accepts `"₱68,440"` and ` 58 `), quarterly periods, and a branch KPI.
- **Every template carries a WORKED EXAMPLE ROW, and it is a `#` comment.** It sits directly above the blank row, shows a filled row column by column, and ends `→ 3.6%` — which is also the answer to "where does the formula happen?": the file holds RAW operands and the value is computed on upload. Being a comment it is stripped by the importer, so a demo number can never be uploaded as real performance. That was the original objection to sample values, and commenting answers both needs at once.
- **The example period is the PREVIOUS one** (`2026-07` above a `2026-08` blank row). Two rows for one period is exactly what the importer rejects, so an example that duplicated it would be a trap for anyone who uncommented it. Uncommenting it is then a legal extra row: verified 2 records, no collision.
- **Example values come from `kpi_input.placeholder`**, which the seeder now carries through from each LOB module's `a_placeholder`/`b_placeholder` (it was discarding them, so all 148 inputs were blank and the Add-Record modal had no hints either). 146 of 148 are populated; the two Nexzys date inputs fall back. Fallbacks: `100` for a number (not 0, which would make half the worked results a division by zero) and dates **latest first**, since `days` KPIs are seeded as `days_between(second, first)` and putting the earlier date first made the example read "−5 days".
- **`example_line()` only prints the `→ result` if those values really evaluate.** A stand-in operand can still divide by zero, and a wrong worked example is worse than none.
- **Adding the example moved every data row down one line.** `importer._rows` computes its offset from the actual comment count rather than a constant, so error messages still name the right spreadsheet row (verified: a bad cell on line 7 is reported as row 7). `HEADER_NOTE` no longer says "these three lines" — it says lines starting with `#` are ignored, and not to remove the first three.
- **An untouched template is now rejected as a WHOLE FILE**, not one "X is required" per row. The blank row ships with its period already filled, so it is not "empty"; it used to produce cell-level issues plus a batch in the import history recording that nothing happened. Now: *"This template has not been filled in yet. Every row has a period but no figures. Enter the numbers under employee_exits, average_headcount, then upload it again."* Nothing written, no batch. This is the likeliest slip now that the file also carries an example.
- **One gap the structural audit could not see, now fixed:** a `days` KPI's template never said what date format it wanted. `records.coerce()` accepts ISO only, so `8/6/2026` was rejected *after* someone had filled the file in and uploaded it. `csv_template.DATE_NOTE` appends "Dates as YYYY-MM-DD" to line 3 when any input is a date. It stays on ONE line: line 1 promises exactly three, and the importer counts comments to work out which spreadsheet row a bad cell was on. Numbers need no equivalent note, since `coerce()` already tolerates `1,234`, `₱1,234` and stray spaces. The Add-Record modal was already fine, rendering `type="date"`.
- `kpi_input.help_text` ("guidance in the CSV's instruction block", §D) is **unused** — nothing sets it and the template does not emit it. Wire it only if per-column guidance is actually wanted; the date note above covers the case that bit.
- **Gotcha — Excel and UTF-8.** A plain UTF-8 CSV opened by double-click on Windows decodes as the ANSI code page, turning `÷ × · —` into `Ã· Ã— Â· â€"`. `csv_template.build_bytes()` prepends a BOM (`utf-8-sig`) — the one signal Excel honours — and the view serves that with `charset=utf-8`. Use `build_bytes()`, not `build()`, from any view.
